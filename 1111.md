# 1111 — PyCSL gaps discovered by formal test 0001

## Context

Proving `pure_lib_test/formal_0001.py` (the formal counterpart of the
concrete write/read round-trip test) uncovered three PyCSL tool gaps.
All three required manual workarounds to reach 18/18 VCs proven.

---

## R5 — String-typed parameters produce WhyML `string`, but API stubs expect `int`

**Symptom:** Declaring `filename: str` in the formal test generates
`formal_test_0001 (filename: string) …` in WhyML. The imported `open` stub
has signature `val open (filepath: int) …`. Why3 rejects the call with:

```
This expression has type string, but is expected to have type int
```

**Root cause:** PyCSL maps all values to `int` in its WhyML model, but the
`string` type annotation on a parameter is preserved literally as WhyML
`string`. There is no coercion or hashing step at the call boundary.

**Workaround:** Remove the `: str` annotation — the parameter defaults to
`int`.

**Required fix:** Either:
- **(a)** Map `str`-annotated parameters to `int` (consistent with the rest
  of the model), or
- **(b)** Introduce a `val function str_to_int (s: string) : int` coercion
  and insert it automatically at call sites where a `string` flows into an
  `int` parameter.

Option (a) is simpler and consistent with PyCSL's current design. Option (b)
is needed only if PyCSL adds a real string theory.

---

## R6 — Imported module constants have no value axiom

**Symptom:** Importing `SEEK_SET` from `pure_lib.os` generates:

```whyml
val constant sEEK_SET : int
```

No axiom binds it to `0`. When calling `lseek(fd2, 0, SEEK_SET)`, the
precondition `how >= 0 and how <= 2` is unprovable — the prover knows
nothing about `sEEK_SET`'s value.

Same issue for `O_CREAT` (64), `O_WRONLY` (1), `O_RDONLY` (0).

**Workaround:** Replace symbolic constants with their literal values (`0`,
`65`, etc.).

**Required fix:** When PyCSL imports a module constant whose value is a
compile-time literal (integer, string hash, etc.), emit either:

- **(a)** An axiom: `axiom sEEK_SET_val : sEEK_SET = 0`, or
- **(b)** A `let constant`: `let constant sEEK_SET : int = 0` (preferred —
  no axiom needed, Why3 inlines it).

This is the same mechanism used for `module_constants` in the os module
itself, but it does not propagate to importing modules.

---

## R7 — Default argument values not supported in cross-module stubs

**Symptom:** `open(filename, O_CREAT | O_WRONLY)` passes 2 arguments, but
the imported stub is:

```whyml
val open (filepath: int) (flags: int) (mode: int) : int
```

Why3 treats partial application as a type error:

```
This expression has type int -> int, but is expected to have type int
```

**Workaround:** Pass the default value explicitly:
`open(filename, 65, 0o777)`.

**Required fix:** When generating cross-module stubs for functions with
default arguments, PyCSL should either:

- **(a)** Emit a wrapper that supplies the default:
  ```whyml
  let open_2 (filepath: int) (flags: int) : int = open filepath flags 511
  ```
  and use `open_2` at call sites with 2 arguments, or
- **(b)** Resolve defaults at the call site during IR construction — if the
  caller passes fewer arguments than the callee's arity, fill in the
  defaults from the callee's signature.

Option (b) is cleaner and avoids wrapper proliferation.

---

## Summary

| ID | Requirement | Workaround used | Blocks |
|----|------------|-----------------|--------|
| R5 | `str` params → `int` in WhyML | Drop `: str` annotation | Any formal test with string parameters |
| R6 | Imported constants need value axioms | Use literal values | Any formal test using module constants |
| R7 | Default args in cross-module stubs | Pass all args explicitly | Any formal test calling functions with defaults |
