## 0. Doctrine — *no-more-int* (governs every fix below)

PyCSL must **stop being int-implemented** and lower each Python type to its faithful WhyML
**type class**, not to `int`. `int` is reserved for genuinely integral values; everything else
gets its real class:

| Python | WhyML class | | Python | WhyML class |
|--------|-------------|-|--------|-------------|
| `int`/`bool` | `int` | | `dict`/`set` | `map 'k (option 'v)` |
| `float` | `real` | | class | record |
| `str` | `string` | | `#@ datatype` | variant |
| `list`/`tuple` | `array int`/`seq int` | | `bytes` | `array int` (byte buffer) |

**Rule:** a fix **MUST NOT** introduce or rely on a value→int coercion (`str_to_int`,
hash-to-int, abstract `(x: int)` op standing in for a typed value) to bridge a faithful type
into `int`. The recurring symptom of the leak is PyCSL falling back to an **abstract int op** —
`subscript_get/set (x:int)`, `iter_length (x:int)`, `join_1 (x:int)`, `val constant N : int`
with no value, an unannotated param defaulting to `int` — whenever it fails to recognize a
type class. Each such fallback against a real-typed value is an `[int-leak]` to retire.

Companion docs: `1111-spec.md` (doctrine statement + R5–R7 import-boundary instances); the
`no-more-int` / `strings-plan` stage comments in `src/pycsl/module6_whyml/`. This register is the
master backlog; `1111-spec.md §9` is the same backlog viewed from the import boundary.

## A. DONE (merged into `main`)

### A1. ✅ Inlined array-temp operation selection (arity2.md 2b) — `f8f3ba8`
`[int-leak, closed]` Inlined array temps were declared `ref (array int)` but operation sites
emitted abstract `subscript_set/get (x:int)` → Why3 type error. Fixed with an op-site-only
`_inline_array_temps` set (`statements.py::_typed_local_vars`), deref-parens for ref-bound temps
(`(!x)[i]`), and param-seeded transitive array propagation. Concrete array ops now used. Drivers
`0583`–`0586`.

### A2. ✅ Bytes-method length postconditions + result typing (1009 R2) — `fe561fc`
`[int-leak, closed]` `s.ljust(w)/rjust(w)/zfill(w)` stubs now emit
`ensures { Array.length result >= x0 }`; a local bound to a bytes-method result is typed
`array int` (was `ref 0`). Bytes treated as the array-int class, not int. Drivers `0588`/`0589`.

### A3. ✅ `\result[N]` tuple-result indexing (1009 R3) — `fe561fc`
Verified already-working for `val` stubs (arity from body return) + tuple-unpack consumers; no
code change. Driver `0587`.

## B. OPEN — high leverage

### B1. ⬜ `[int-leak]` Global/record **array-field** subscript reads → abstract `subscript_get`
**The real `os`-module unblocker** (not in `1009.md`). Reading a global record's array field,
`d.disk[3]`, emits `subscript_get d.disk 3` (`val subscript_get (x:int)(i:int):int`) but
`d.disk` is `array int` → hard type error. A textbook leak: a real `array int` value forced
through the abstract int op.
- **Root:** `expressions.py::_handle_subscript` (~`:1349-1398`). The read-path `is_array`
  decision does not resolve a record field's declared type; `_field_type_of` (`types.py`,
  global-aware since `35441ec`) is consulted at the array-**set** site but not consistently at
  the **read** site (`:~1361`).
- **Faithful fix:** when the subscripted value is an `Attribute`/`FieldGet` whose
  `_field_type_of` ∈ `list/tuple/bytes/bytearray`, take the concrete array-read branch
  (`(d.disk)[i]` + `Array.length` bounds), mirroring the set site. Never `subscript_get`.
  Plausibly report.md's **45 "Index in array bounds"** failures.
- **Driver:** positive (read under invariant) RED→GREEN; negative (OOB index unprovable).

### B2. ⬜ `[int-leak]` `bytes`/`bytearray` → `array int` in `_symtype_to_whyml`
`functions.py::_symtype_to_whyml` (`:659`) maps `list`/`tuple`→`array int` but drops
`bytes`/`bytearray`→`int`. This split representation is the root of the worst `pure_lib/os`
deformation (a `-> bytes` helper relabelled `-> list`, a type-incoherent lie). Bytes ARE the
byte-buffer class.
- **Faithful fix:** add `bytes`/`bytearray` to the `array int` arm. Unifies the split (bytes
  already reaches `array int` elsewhere via the `\valid`/array1d path, `functions.py:~154`).
- **Risk:** broad — every `bytes`-typed param/return/symbol re-lowers; full sweep + byte-diff.
- **Enables:** D1 (restore faithful `-> bytes` annotations).
- **Driver:** a `-> bytes` function returning `bytes([...])`, inlined, element read.

## C. OPEN — medium

### C1. ⬜ `[int-leak]` Bytes-method **fill-char** argument typed `int`
`s.ljust(30, b'\x00')` — the fill `b'\x00'` lowers to `array int` (`(let _alit = Array.make 1 0
in _alit)`) but `_call_bytes_methods` types arg `x1` as `int` → type error. (A2 was therefore
gated with `zfill` (width-only).) A bytes value forced into an int param slot.
- **Root:** `expressions.py::_call_bytes_methods` (~`:1268-1283`). The `_ARR` prefix check
  misses the `(let _alit = Array.make …` array-literal shape → typed `int`.
- **Faithful fix:** recognize the `(let _alit = Array.make …` (and bytes-literal IR) shape as
  `array int` in the arg-typing loop; or type the fill arg of `ljust/rjust` as `array int`.
- **Driver:** `s.encode().ljust(30, b'\x00')` into `\valid(x,30)`, prove.

### C2. ⬜ `[int-leak]` Tuple-typed **local** body subscript `p[0]` → `subscript_get`
`p = unpack_pair(d); p[0]` (tuple local) emits `subscript_get !p 0` against a `(int,int)` → type
error. Only `\result[N]` (the `Result` node, A3) destructures; a tuple-typed Var local does not.
A real tuple forced through the abstract int op.
- **Root:** `expressions.py::_handle_subscript` (~`:1303`) — destructure arm gated on
  `value.type == "Result"`. The `os` module sidesteps via tuple-unpack (`a,b=f()`), so not
  blocking there; lower priority.
- **Faithful fix:** extend the destructure to a Var of known tuple arity → `(let (_r0,_) = !p in
  _r0)`.
- **Driver:** `p = f(); return p[1]` for tuple-returning `f`.

### C3. 🔶 `[int-leak]` Tuples-in-arrays — REJECTED (silent collapse closed); full model = **G1**
`_unpack_direntry -> tuple` and `_read_directory` returning a list of tuples forced the
`listdir`/`scandir` consumer rewrites in `8d9f749`. PyCSL has no faithful array-of-tuples class.
- **Landed (`cd00e92`):** the *unsound silent collapse* (each tuple element → an int hash) is
  closed — an array/list of tuples is now an explicit hard error ("use parallel arrays"), driver
  `0601`. This stops the leak but does not yet *support* the construct.
- **Remaining (the faithful support):** a real `array (tuple)` model — see **G1** below. Until
  then `pure_lib`'s `listdir`/`scandir` (D3/D5) must use parallel arrays, not arrays of tuples.

### C4. ⬜ Bitwise `~` (NOT) unsupported — *not an int-leak* (genuine int op)
`_set_bitmap` was rewritten to avoid `~`. Bitwise NOT is a legitimate operation on the `int`
class, so this is ordinary feature work (support `~` as `-x - 1` on the int model, or a BV op if
a bitvector theory is in use), not a type-class violation.
- **Driver:** `x & ~mask`.

### C5. ⬜ `[int-leak]` String-valued module constants fold to an int hash
Surfaced by the doctrine (and `1111-spec §9`): a `str` module constant currently folds to an int
hash rather than a Why3 `string` literal. String identity must be `string` equality, not a hash.
- **Faithful fix:** once R6 (`1111-spec`) generalizes constants to the type class, a `str`
  constant emits `let constant N : string = "…"`. Couple with the strings-plan.

## G. FUTURE — larger type-class models (no-more-int, substantial)

New WhyML type classes, each a multi-stage feature (its own plan), not a leak-patch. Promote to
B/C when a real driver demands it; until then the current behaviour is a *sound rejection*
(C3 / G1) rather than a silent collapse.

### G1. ⬜ `[int-leak]` Faithful `array (tuple)` model (replaces C3's rejection)
Today an array/list of tuples is hard-rejected (C3, `0601`). The faithful model lets it be
*supported*: a list of fixed-arity tuples lowers to a Why3 `array (int, …)` (or `array recordT`
for a named tuple/record element), with element read `a[i]` returning the tuple and `a[i][k]`
destructuring it (reuse the C2 tuple-local machinery: `_collect_tuple_var_assigns` /
`_ghost_tuple_vars` and the `(let (_r0,…) = … in _rk)` destructure).
- **Touch points (sketch):**
  - element type inference: a `ListLit`/`ArrayLit` of `Tuple` elements → element arity + per-slot
    types (replace the C3 reject in `expressions.py::_expr_to_whyml` ArrayLit arm).
  - construction: `Array.make N (e0_tuple)` with tuple-valued slots (not int-coerced).
  - typing: `_symtype_to_whyml` / `_compute_return_type` / `_param_type_str` learn an
    `array (tuple)` / `array recordT` return-and-param type; `find_array_and_dict_vars` tracks
    such locals.
  - subscript: `a[i]` returns the tuple (concrete `Array.get`); `a[i][k]` destructures.
  - `\valid`/`\length` already generalise (length is element-count).
- **Decision to make first:** anonymous `array (int,int)` tuples vs. requiring a named
  `#@ datatype`/record element (cleaner Why3, matches the record path already built). Likely
  start with fixed homogeneous-int tuples (`array (int,int)`), the `_read_directory` shape.
- **Enables:** the pure_lib agent to restore the faithful `_read_directory` /
  `scandir`/`listdir` (D3/D5) instead of the parallel-array workaround.
- **Gate:** positive driver (build, read element, destructure, prove) RED→GREEN; the existing
  `0601` reject-driver flips from XFAIL to a *supported* positive (or is retired) when G1 lands.
- **Effort:** large (new type class). Own plan when scheduled.
