## 3. The PRECISE obstruction (why read-side ≠ write-side)

I read the emitted `.mlw` body and **all** `dir_lookup`-touching axioms. The fidelity
ensures is unreachable for THREE compounding, independent reasons — the third is fatal
and read-side-specific:

### (a) The body never materializes the byte-decode trigger
Emitted body reads `Array.sub self.dir !entry_offset 32` then `_unpack_direntry entry`
— it produces NO `self.dir[blk*512+32*k]` term. The banked bridges
`slot_inode_byte_decode` / `slot_name_byte_decode` key on `[disk[blk*512+32*k]]` /
`[disk[blk*512+32*k+2]]`, so they **never E-match the read body** (same "narrow trigger
never fires on the real body" finding the write-side hit, here with no fix lever: the
write side could literal-offset the *blit*; the read side reads through `Array.sub` +
the opaque `_unpack_direntry`).

### (b) The name is a fully-opaque hash constant — Gap 5 at the read site
Emitted: `name := decode_1 1501791143`, and the compare lowers to
`!name = str_hash_op pathname`. The decoded name is a **constant hash with zero
dependence on `self.dir` bytes** (the byte→str codec is unmodeled, Gap 5). There is no
bridge from this to `slot_name(self.dir, 5, i)`. The mutation side dodged this because
the write helper *writes* the bytes it controls; the read side must *recover* the name
from disk bytes through the opaque codec — exactly the unmodeled direction.

### (c) FATAL & read-side-specific: there is NO value-correspondence axiom for `dir_lookup`
Surveying every emitted `dir_lookup` axiom:
- `scan_reflects_present` — IFF on **SIGN** only: `dir_lookup >= 0 <-> ∃ live match`.
- `dir_lookup_frame` — frame: all slots agree ⟹ `dir_lookup` agrees.
- `remove_reflects_absent` — gives `dir_lookup < 0` under absence hypotheses.
- `dir_blit_marker_*` — WRITE-side, relate POST-write `slot_inode/slot_name` to
  written bytes.

**None states `dir_lookup`'s VALUE** (e.g. `dir_lookup == slot_inode of the last live
matching slot`). The Rocq kernel `UnixDirScan.v` *does* compute the value — `dir_lookup
:= scan … 16 (-1)`, a Fixpoint keeping the last match's `slot_inode` — but the WhyML
model deliberately exposes only the **sign-IFF** (the value form would re-introduce the
gap-9 existential blowup the IFF was crafted to avoid). The FIDELITY ensures is a full
**VALUE equality**, so even with (a) and (b) bridged it has no axiom to land on. This is
the keystone: the write side's marker carries `slot_inode(post,s)==256*b0+b1` as a
VALUE; the read side has no symmetric `dir_lookup == <closed-form scan value>` rung,
and authoring one re-opens the very existential E-matching wall the abstract model was
shaped to suppress.

**Summary of the bundle:** retiring `_dir_lookup` requires (i) a body whose read path
materializes the byte triggers (it does not, and `Array.sub`+`_unpack_direntry`+opaque
`decode_1` give no lever), (ii) a name-content bridge across the unmodeled Gap-5 codec
at the READ direction, AND (iii) a NEW value-level scan-correspondence axiom for
`dir_lookup` that does not currently exist and whose value form re-explodes the
existential web. A `\trusted` is all-or-nothing per method; all three must hold.

## 5. The doctrine-clean close (human-gated, NOT autonomous)

Closing this is a **substantial, human-gated model decision**, not a `\trusted` and not
an autonomous loop move. It requires BOTH:

1. **A new cross-validated VALUE axiom** `dir_lookup d blk name = <closed-form last-live-

   `Array.sub`/`_unpack_direntry` path give no lever to surface the byte triggers, unlike

Until both land, `_dir_lookup` stays a LOGGED GAP routed to the human, exactly like the
