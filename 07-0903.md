## 0. Background you need to read these items (self-contained)

### 0.1 The *no-more-int* doctrine
PyCSL translates annotated Python into WhyML, which a prover (Why3 + SMT) checks. Historically
PyCSL modelled **every** value as a WhyML `int`. That is convenient but *unsound by convenience*:
it makes `"a" == "b"`, list aliasing, and floating rounding indistinguishable from integer facts.
An ongoing program — "no-more-int" / "de-int-ification" — replaces the int-everywhere model,
type by type, with each Python type's **faithful WhyML type class**:

| Python | Faithful WhyML class | | Python | Faithful WhyML class |
|--------|----------------------|-|--------|----------------------|
| `int`/`bool` | `int` (the only types that stay int) | | `dict`/`set` | `map 'k (option 'v)` |
| `float` | `real` | | class instance | record |
| `str` | `string` | | `#@ datatype` | variant |
| `list`/`tuple` | `array int` / a tuple type | | `bytes` | `array int` (byte buffer) |

**Governing rule:** no feature may introduce a value→int coercion (string hashing, "model X as
int", an abstract `(x: int)` op standing in for a typed value) to bridge a faithful type into
`int`. Where a construct cannot be lowered faithfully, the translator must **reject it with a
diagnostic** (a *sound rejection*), never emit ill-formed output or silently change meaning.

### 0.2 The lowering's output contract
Generated WhyML must be **well-formed** (parses & type-checks), **self-contained** (imports
everything it references), and **faithful** (its meaning equals the source's — no dropped
operand, receiver, or type). Most remaining items are a faithful-type or output-contract gap.

### 0.3 Scope / ownership (important)
Two agents work this codebase in parallel:
- **PyCSL-tool track** — `src/pycsl/**` (the Module 1–6 compiler, inliner, WhyML emission). Items
  **W1–W4** belong here. Each lands with a self-contained reference-corpus driver
  (`test-suite/corpus/pycsl-reference/`, plus a `multi_file_lib/` fixture if cross-module) and a
  clean full `bin/run-reference-tests.sh` sweep + a before/after WhyML byte-diff.
- **pure_lib track** — `pure_lib/**` (the verified standard-library stubs). Items **W5–W6** belong
  to that agent; the tool fixes that *enable* them are already merged. The tool agent must **not**
  edit `pure_lib/`.

### 0.4 What is already done (context, not to redo)
For orientation: bytes-as-array (`0442` B2), record array-field reads (B1), bitwise `~`,
fill-char typing, string constants, tuple-local `p[i]`, the array-of-tuples **rejection** (C
series); cross-module type/constant/default fidelity (`1111` R5/R6/R7); reserved-word type names,
isinstance collision, string-`in` import closure, computed-receiver predicates, class-return
typing (`07-0647` R8–R13 core). All merged to `main`. The items below are what those efforts
*left open*.

## W1 — Faithful array-of-tuples (and array-of-record) model
**Origin:** `0442.md` G1 (supersedes the C3 *rejection*). **Owner:** PyCSL-tool. **Effort:** large
(a new type class). **Status:** not implemented.

### Intent — why this is useful
A great many real programs store **lists of small fixed-shape tuples**: a directory table of
`(inode_number, name)` entries; a list of `(key, value)` pairs; coordinate lists `[(x, y), …]`; a
parser's token stream `[(kind, text), …]`. Today PyCSL has no WhyML type for "an array whose
elements are tuples". After the de-int-ification work it does the *honest* thing — it **rejects**
such a literal with a clear error ("array/list of tuples is not supported; use parallel arrays")
rather than the previous behaviour of silently hashing each tuple to one integer (which lost all
structure and was unsound). That rejection stops the unsoundness but also stops the *use*: any
module built around lists of tuples cannot be verified at the body level, and authors must
contort their code into parallel arrays (which the `pure_lib/os` directory code was forced to do).
The intent of W1 is to make the construct **first-class and provable**, so structure is preserved
end to end: element `a[i]` is a tuple, and `a[i][k]` is its k-th field.

### Requirement
- **Element typing.** A `list`/`array` literal whose elements are tuples (uniform arity and slot
  types) is given a WhyML element type — either an anonymous tuple `(int, …)` or, where the
  elements correspond to a declared class/`#@ datatype`, a named `record`/variant — yielding an
  `array (int, …)` / `array recordT`.
- **Construction** lowers the literal to that array type with tuple-valued slots (never int-coerced
  elements). This replaces the current hard-rejection in the array-literal lowering.
- **Typing through the pipeline.** Parameter, return, symbol-table, and return-type inference learn
  the `array (tuple)` / `array recordT` type; the array-local detector tracks such locals.
- **Access.** `a[i]` returns the tuple/record (concrete `Array.get`); `a[i][k]` destructures the
  k-th component (reuse the tuple-local destructure machinery already built for `p[i]`).
- **`\valid` / `\length`** generalise unchanged (length is the element count).
- **First design decision (record before code):** anonymous homogeneous-int tuples
  (`array (int, int)`, the directory shape) are the smallest useful start; a named-record element
  is cleaner in Why3 and aligns with the existing record model. Pick one and document it.

### Acceptance
A driver that builds a list of tuples, reads an element, and destructures a component **proves**;
the existing array-of-tuples *rejection* driver flips from an expected-failure to a supported
positive (or is retired).

### Dependencies / enables
Builds on the existing tuple-local and record machinery. **Enables** the pure_lib unwind of the
`scandir`/`listdir`/`_read_directory` rewrites (part of W6).

## W2 — `\result` structured access in contracts (record fields and tuple/array elements)
**Origin:** `07-0647-spec.md` R13 residual (distinct from R13's body type-mismatch, which is
fixed). **Owner:** PyCSL-tool. **Effort:** medium. **Status:** not implemented (field access);
partially present (tuple index).

### Intent — why this is useful
PyCSL can now *return* a class instance or a tuple with a faithful type (a constructor/factory
`make() -> Box`, an unpacker `unpack() -> (int, int)`). But a return type is only half useful if
you cannot **state what the result is**. To specify such a function you must write a postcondition
about the returned structure — `#@ ensures \result.balance == initial`, `#@ ensures \result[0] >= 0`.
Today `\result.field` (field access on the result in a contract) does not parse, so a
class-returning function can carry only a vacuous `ensures True` — it proves nothing about what it
builds, defeating the point of verifying a factory at all. (The tuple form `\result[k]` already
works in `ensures`; the gap is record-field access, and `\result[i].field` for an array-of-tuple
element, which depends on W1.)

### Requirement
- The contract grammar accepts `\result.<field>` (field access on `\result`) and, with W1,
  `\result[i].<field>`.
- Semantic resolution checks the field/index against the function's declared return type
  (record/variant/tuple/array element).
- Lowering emits `\result.field` as the record field projection on the WhyML `result`, and
  `\result[k]` as the tuple destructure (the body-side `\result[i]` destructure already exists —
  extend it to the spec-side field case).

### Acceptance
A class-returning function proves `#@ ensures \result.<field> == <expr>`; a tuple-returning
function proves both `\result[k]` (already) and a record-field variant.

### Dependencies
Independent for the record-field case; the `\result[i].field` (array-of-tuple element field) case
depends on **W1**.

## W3 — Receiver (`self`) fidelity across *all* method-to-function extraction shapes
**Origin:** `07-0647-spec.md` R11 residual (invariant S3.1). **Owner:** PyCSL-tool. **Effort:**
small–medium (reproduce first). **Status:** holds for ordinary methods; one extraction shape
unconfirmed.

### Intent — why this is useful
When PyCSL lowers an instance method into a module-level WhyML function, the receiver (`self`)
must be a parameter so the body's references to `self` and its fields resolve. For ordinary
methods this holds. But the original report (`07-0647` R11) observed a *specific* extraction path
(named `_color_match_group`) where `self` was **omitted** from the generated signature, producing
`unbound function or predicate symbol 'self'` — making body-level verification of that method
impossible. The spec invariant (S3.1) requires the receiver to be present for **every** extraction
shape, not just the common one. This is a completeness/robustness item: a single path that drops
`self` silently blocks verification of any method shaped like it. Verifying real OO code (e.g. the
`pure_lib/re` engine's match/group methods) needs the invariant to be universal.

### Requirement
- Identify the extraction path that can omit `self` (the `_color_match_group` shape — a method
  extracted to a module-level `let` in a particular context, possibly involving nested/inner
  methods, comprehension-lifted helpers, or a specific decorator/return pattern).
- Guarantee `self` is always the first parameter of an extracted instance method.
- Build a reference driver reproducing that exact shape (this could not be reproduced from the
  basic-method case during the prior pass — the reproducer is the first deliverable).

### Acceptance
A driver in the shape that triggered the original omission verifies with `self` bound; ordinary
methods remain unaffected.

## W4 — Excise the accidental ~35 k-line vendored CPython `lib/` dump
**Origin:** `0442.md` F1. **Owner:** repo maintenance (tool side; needs a decision). **Effort:**
small but requires a call. **Status:** not done. **Non-blocking.**

### Intent — why this is useful
A prior "Fix os module" commit accidentally swept the entire vendored CPython `lib/` tree
(`argparse.py`, `ast.py`, `typing.py`, `inspect.py`, …) — about 35,000 lines — into history,
inside a commit whose actual change was ~70 lines. This bloats the repository, makes `git blame`
and diffs noisy, renders that commit unreviewable, and muddies which code is intentionally
maintained vs. vendored/fetched. The intent is hygiene and provenance clarity: the history should
reflect intentional changes, and any vendored dependency should be clearly labelled as such.

### Requirement
Decide whether `lib/` is a needed vendored dependency or a derived/fetch artifact. If needed,
isolate it into its own clearly-named vendoring commit (and document its source/version); if not,
remove it and add it to `.gitignore`.

### Acceptance
`lib/` is either an intentional, documented vendoring or absent + ignored; no future "fix" commit
re-absorbs it.

## W5 — Library type-annotation sweep (`pure_lib`)
**Origin:** `1111-spec.md` R5.3 / §9. **Owner:** **pure_lib agent** (NOT the tool track).
**Effort:** medium (library-wide). **Status:** not done.

### Intent — why this is useful
The tool now carries **real types across the import boundary** (a `str` argument flows as a Why3
`string` into a `str`-typed stub parameter — no int hash). But this only helps when the library
*source* annotates its parameters truthfully. For example `os.open(filepath, flags, mode=0o777)`
leaves `filepath` unannotated, so the generated stub types it as `int`; a string-literal filename
from a caller then mismatches the stub. The sweep annotates every `pure_lib/*` parameter that
denotes a string/list/dict/bytes/etc. to its real Python type, so each generated stub signature is
faithful and callers type-check without contortion. Crucially this is **telling the truth about
types**, not a deformation — contrast the earlier `pure_lib/os` edits that *lied* about types
(relabelling a `-> bytes` body as `-> list`). It is the consumer-side completion of the merged R5
tool fix; without it, the real `os`/`re` modules do not benefit from R5.

### Requirement
Audit `pure_lib/*` for parameters (and returns) whose real type is non-int (str/list/dict/set/
bytes/float/class) and are currently unannotated or mis-annotated; annotate them to their faithful
Python types; re-verify the affected modules.

### Acceptance
A formal test importing the annotated library proves with string/list/dict arguments passed
directly (no annotation-dropping workaround), the generated stub signatures showing the real
types.

## W6 — Unwind the `pure_lib/os` faithfulness deformations + republish an honest `report.md`
**Origin:** `0442.md` D1–D5 (arity2.md Phase 4); rationale in `comment.md`. **Owner:** **pure_lib
agent.** **Effort:** medium–large (library edits + re-verify ~4,000 VCs). **Status:** not done.

### Intent — why this is useful
To reach a 93.4 % headline on the `os` module, the library was **deformed** to fit the tool's
then-current limits. Specifically: a `-> bytes` helper was relabelled `-> list` while its body
still returned `bytes` (a type-incoherent lie); real postconditions like `\result >= 0` were
replaced with vacuous `ensures True`; `scandir` was made to yield raw inode integers instead of
`DirEntry` objects (breaking the real `os.scandir` API contract); `DirEntry.path` lost its leading
`/`; and `listdir`/`scandir` were rewritten to scan the disk directly to avoid lists of tuples.
Each trades **library faithfulness for a headline number** — the exact opposite of the EXTREME
RIGOR principle. Several of those vacuous-`True` goals also inflate the 93.4 % figure: it is not
93.4 % of *meaningful* assurance. Now that the enabling tool gaps are closed (bytes-as-array,
record array-field reads, …), these deformations should be reversed so the library again models
real `os` semantics, and the result re-measured honestly.

### Requirement
- Restore `-> bytes` return/param types (enabled by the merged bytes-as-array work).
- Restore real postconditions where `ensures True` was substituted; anything still unprovable
  becomes a tracked `# TODO` with a reason, never a silent `True`.
- Restore faithful semantics: `scandir` yields `DirEntry` objects; `DirEntry.path` keeps its
  leading `/`; `listdir`/`scandir` go back through `_read_directory` (depends on **W1** for
  arrays of tuples).
- Re-run and **republish `report.md`** with an honest Valid/Timeout/Unknown tally; the restored
  number is the real assurance even if lower than 93.4 %.

### Dependencies
`-> bytes` restore and real postconditions are doable now; `scandir`/`listdir` restore depends on
**W1**. The whole item is gated on the tool fixes it relies on already being on `main` (they are,
except W1).
