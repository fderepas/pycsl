# 08-0350-spec-rev2 — `pure_lib/astmod` contracts **and** the `exec`/`eval`/`compile`/`ast.parse` parser family (P5)

**Date:** 2026-06-08
**Status:** Draft (rev. 2)
**Supersedes:** `08-0350-spec.md` (2026-06-08), `ast-req.md`
**Scope:** (a) replace the opaque `astmod` stub with bucketed contracts for verifying **user code that
imports `ast`** (rev1, unchanged in substance below); **(b) NEW — integrate `07-1839` P5**: the
`exec`/`eval`/`compile`/`ast.parse`/`literal_eval` family, unified by the observation that in CPython
they all invoke the **same parser front-end**. The two halves meet at one place: a *string argument*
is either a **compile-time constant** (the tool can parse/evaluate it at verification time) or
**dynamic** (unknowable → conservative havoc/`\trusted`).
**Ownership split (important).** The astmod *contracts* (§4–§9) are **pure_lib** (another agent's
domain). The P5 *family handling in the transpiler* (§11) is the **PyCSL tool** (my domain, the
`07-1839` P5 phase). rev2 specifies both so the seam between them is explicit; each half lands in its
owning track.

## 1  Context

The PyCSL toolchain contains a 3,775-line pure-Python reimplementation of the stdlib `ast` module
(`src/pycsl/pure_ast.py`). Every pipeline stage imports it:

| Consumer | Key functions used |
|---|---|
| Module1_Ingestor | `parse`, `comments`, `walk`, `iter_child_nodes` |
| Module3_Weaver | `parse`, `walk`, `iter_child_nodes`, `NodeVisitor`, `unparse`, `literal_eval` |
| Module4_SemanticAnalyzer | `NodeVisitor`, `walk`, `iter_child_nodes` |
| Module5_IREmitter | `NodeVisitor`, `walk`, `iter_child_nodes`, `get_docstring`, `unparse`, `literal_eval` |
| import_classifier, pycsl.py, ConcurrencyChecker | `parse`, `walk`, `iter_child_nodes`, `dump` |

`pure_lib/astmod/__init__.py` is currently a stub: every AST node is an opaque non-negative `int`
handle and every function a trivial body. So formal tests assert only non-negativity/identity, and
user code that imports `ast` can be verified only up to type compatibility.

**The irony, named and resolved.** `pure_ast.py` is the parser the toolchain *itself* runs, so
`astmod` is a contract for PyCSL's own front-end. That tempts a second, grander reading — using
`astmod` to *self-verify* the parser. **This spec explicitly does not pursue that** (see §2). The
parser stays in PyCSL's trusted base; `astmod` over-approximates it solely so that *user* programs
calling `ast` can be verified.

**rev2 framing — one front-end, two surfaces.** `ast.parse(s)` is the *data* surface of the parser
(source → an AST value the program inspects). `exec(s)`/`eval(s)`/`compile(s)` are the *executable*
surface (source → behaviour) of the **same** parser. `literal_eval(s)` is the restricted-evaluator
surface. Whatever decides what a *constant* `s` means must be the same for all of them — they cannot
be allowed to diverge on the same string. §11 makes that unification explicit.

## 2  Goal — and explicit non-goal

**Goal (a): let user code that does `import ast` verify against meaningful postconditions** — not
just `>= 0`. Concretely, a verified user program may rely on:

1. The **faithful** identity/projection facts (§4.1): `copy_location(n, o) == n`,
   `fix_missing_locations(n) == n`, `increment_lineno(n) == n`.
2. **Referential transparency** of the pure helpers: because `parse`/`dump`/`unparse` carry
   `assigns \nothing`, PyCSL's RT inference (`module5/memoization_rt.py::_detect_purity`, reference
   §2.6 D3) treats them as pure, so `dump(parse(s))` evaluated twice on the same `s` yields **equal**
   results (an abstract `val` is a deterministic function of its arguments — same `s` ⇒ same handle).
   This is *determinism-via-purity* — it does **not** characterize *which* string is produced (see the
   Ledger, §8).
3. Eventually (Phase 2–3), **`isinstance` dispatch on node types** — the common user idiom — once
   nodes carry a real `τ` tag and `\subtag`/`\typeof` land.

**Goal (b) — NEW (P5): a sound, unified model of the executable/eval parser family** (`exec`, `eval`,
`compile`, `ast.parse`, `literal_eval`) so that user code using them verifies — *faithfully* when the
source is a compile-time constant, *conservatively* (havoc + `\trusted`) when it is dynamic — with
the same verdict for the same string across the whole family.

**Non-goal: self-verification of `pure_ast.py`.** `astmod` contracts *over-approximate* the parser;
a green `astmod` test proves facts about the *contract*, not about the 3,775-line body. The body is
TCB. Nothing here narrows that TCB.

## 3  Classification lens (modelled / specified / stubbed)

Per the project discipline, every function is bucketed and **coverage is reported per bucket**:

- **Modelled** — a faithful contract preserving real semantics (a real proof).
- **Specified** — an axiomatized contract trusted as written; enters the TCB; sound only for the
  stated property (e.g. "returns a `str`," not *which* string).
- **Stubbed** — signature/handle only; proves nothing about the value.

The word "faithful" is reserved for the **Modelled** rows. P5 adds a fourth, *orthogonal* axis —
**knowability of the argument** (constant vs dynamic) — which can *promote* a normally-stubbed
function (`literal_eval`, `eval`) to **Modelled** on a constant argument (§11.3).

### 4.4  Soundness fix — `literal_eval` (rev2: split by knowability)

The earlier `ensures \result >= 0` "for numeric literals" is **unsound**: `literal_eval("-5") == -5 < 0`,
and for list/dict/str results an `int`-handle cannot represent the value. Two corrections:

- **(rev1, kept) Dynamic argument → honestly stubbed.** `literal_eval(s)` for non-constant `s` returns
  an **unconstrained** handle (no `>= 0`); value not modelled. Also note the `int` handle is itself a
  *no-more-int leak* (the real result is int/str/list/dict/tuple/bool/None) — acceptable only while
  Stubbed; a real model gives the result the literal's true `τ`.
- **(rev2, NEW) Constant argument → Modelled.** `literal_eval("[1, 2]")`, `literal_eval("-5")` etc. are
  **compile-time-knowable**: the tool can parse and evaluate the literal at verification time and emit
  the *actual* value with its true type (`-5 : int`, a 2-element list, …). This is the P5 family rule
  (§11.3) applied to `literal_eval`, and it is the *faithful* answer the `int`-handle could never give.

## 5  Node type classes (`_NODE_SPEC`) and `isinstance`

`pure_ast.py` generates ~90 node classes; user code relies on `isinstance(node, ast.FunctionDef)`.

- The mechanism is **`\subtag(\typeof(node), FunctionDef_tag)`** (per `07-1839` §4.2 / P4 — now landed
  on `main`) — **not** `\in_globals` (a category error for a *type* test).
- **`\typeof` is decided only when the node carries a concrete `τ`** (decision B). Today `parse` returns
  an `int` handle (`τ = Any`), so `\typeof(node)` is in the unknown tail and `isinstance(node, …)` stays
  **symbolic**. To decide it, nodes must be a real `variant`/`record` type — Gap 6/7.
- **Phase 3 `isinstance` needs both P4 *and* the node-class model.**
- **rev2 link to P5:** a node produced by `ast.parse("<constant>")` (§11.3) *could* carry a concrete `τ`
  derived at verification time (e.g. the root is `Module` for `mode="exec"`, `Expression` for
  `"eval"`), making `isinstance` on *that* node decidable even before the full Phase-2 model — a
  constant-source special case, gated on a driver.

## 11  P5 — the `exec`/`eval`/`compile`/`ast.parse`/`literal_eval` family (NEW)

### 11.1  Two parsers, never conflated

| | What it is | Used for |
|---|---|---|
| **Tool compile-time parser** | host `ast.parse` in `Module1_Ingestor` (line ~112, already there) | parsing the source under verification — **including any constant string passed to the family** |
| **`pure_lib/astmod`** | the runtime *model* of `ast` for verified programs | a verified program that calls `ast.parse(x)` and inspects the result at runtime |

The family's executable members (`exec`/`eval`/`compile`) have **no** runtime data surface to model —
their effect is on *behaviour/scope*, not a returned AST — so they never route through `astmod`. They
route through the **tool** (constant → splice/evaluate; dynamic → havoc). `ast.parse`/`literal_eval`
have a data result and so *also* touch `astmod` for the runtime-model case.

### 11.2  The one classifier: knowability of the source argument

For every family call `g(s, …)` with `g ∈ {exec, eval, compile, ast.parse, ast.literal_eval}`:

- **`s` is a compile-time constant** (a string literal, or a local provably bound to one — reuse the
  P3 definite-assignment / constant-folding the tool already has) → **compile-time-knowable**. The tool
  parses/evaluates `s` *at verification time* with its own parser (§11.3). This is the
  "introspection = compile-time knowledge" principle, identical in spirit to `\in_globals`/`\typeof`.
- **`s` is dynamic** (any non-constant) → **unknowable**. *Nothing* — not the tool, not `astmod` — can
  determine the code. Apply the conservative treatment (§11.4), **identically for every member** so
  `exec(s)` and `ast.parse(s)` on the same dynamic `s` cannot diverge.

This single split is the *source-of-truth squeeze* for the family: the English (each function's docs)
and the reference implementation (CPython's one parser) agree that all five share a front-end, so the
verifier must give one answer per string — faithful where the string is pinned, trusted where it is not.

### 11.3  Constant source → faithful (Modelled)

| Member | Constant-arg behaviour | Result |
|---|---|---|
| `exec("…stmts…")` | **whitelist splice** at verification time | the parsed statements are spliced into the IR with line-preservation; introduced names enter the P3 dataflow. **Whitelist = assignments + pure expressions only**; **reject** (fail-loud `[parse]` error) `return`, `while`/`for` *without* an invariant, `import`, nested `def`/`class`, nested `exec`. |
| `eval("…expr…")` | parse + lower the expression | a value with a decided `τ` (so downstream `isinstance`/arithmetic on it decides). |
| `literal_eval("…literal…")` | parse + evaluate the literal | the **actual value** with its **true type** (`-5:int`, `[1,2]:list`, `"x":str`, `{…}:dict`, `True:bool`, `None`). Faithful — supersedes the §4.4 `int` handle for this case. |
| `compile("…", mode)` / `ast.parse("…", mode)` | parse | (with Phase-2 node `τ`) an AST value whose **root `τ`** is `Module` (`mode="exec"`) or `Expression` (`"eval"`), enabling §5's constant-source `isinstance`. Until Phase 2, the handle as today, but the *mode→root-type* fact is recordable. |

These promote to **Modelled** on a constant argument — the knowability axis (§3) overrides the
default bucket.

### 11.4  Dynamic source → conservative (Specified/`\trusted`)

A dynamic `s` is the halting problem; mark the call site `\trusted reviewer: dynamic-exec`. It is **not**
a no-op:

1. **Scope havoc (decision C, already wired).** A function containing a dynamic family call sets
   `has_dynamic_exec = True`; the tool consumes it as `_scope_dyn_exec`, which **withholds the
   `\in_scope` decided-false direction** downstream (a dynamic `exec` can inject any name). *(This hook
   already exists on `main` from P3; P5a only needs to SET the flag.)*
2. **Frame taint.** A dynamic `exec`/`eval` is a **worst-case mutator**: any surrounding `assigns` /
   HAPPY confinement must treat it as able to write anything (the same rule the reference applies to a
   non-exempt `\trusted`/`\abstract` mutator without `#@ \preserves`). It taints integrity claims in
   its scope.
3. **No decided result.** `eval(dynamic)`/`ast.parse(dynamic)`/`literal_eval(dynamic)` return an
   unconstrained value (no `>= 0`, no `τ`) — `astmod`'s Stubbed rows (§4.3/§4.4) are exactly this case.

### 11.5  Soundness

The only unsound outcome would be *deciding* something about a dynamic string — never done. Constant
→ faithful (the tool genuinely knows the code); dynamic → trusted/havoc (sound, conservative). Same
string ⇒ same verdict across the family (§11.2), so no member can be used to launder a fact another
member would refuse. This is the family analogue of the `07-1839` three-valued fail-safe: a missing
proof or a `\trusted`, never a wrong one.

|---|---|---|
| **P5a** dynamic family → conservative | detect `exec`/`eval`/`compile`/`ast.parse`/`literal_eval` with a non-constant arg → set `has_dynamic_exec`; wire the frame taint | **[PROVE]** after a dynamic `exec`, a previously decided-false `\in_scope(x)` is **withheld** (driver); **[review]** dynamic exec taints `assigns`/HAPPY |

## 8  Soundness Ledger (what a green run does NOT guarantee)

| Entry | Not guaranteed |
|---|---|
| `pure_ast.py` body | **Not verified** — TCB; `astmod` over-approximates it |
| `parse` (dynamic / pre-Phase-2) | nothing about the *tree* — only a non-negative handle |
| `dump`/`unparse`/`get_docstring` | *which* string — only `str` + purity (RT = equal-on-equal-input) |
| `literal_eval` (dynamic) | nothing about the value (opaque handle; **no** `>= 0`) |
| `walk`/`iter_*` | the actual yields — only a count proxy (`walk`: `>= 1`) |
| `isinstance` (pre-Phase 3, non-constant source) | type membership — `τ(node)=Any` ⇒ symbolic |
| **`exec`/`eval`/`compile` (dynamic)** | **anything about the executed code; treated as a worst-case mutator (`\trusted`) that havocs scope** |
| **constant family results (P5b–d)** | **only as faithful as the tool's own parser — which is the same TCB front-end as Module1** |

A `--soundness-report` marks which user-code VCs rest on the Specified/Stubbed/`\trusted` rows.
