# 07-0647-spec.md — specification: well-formedness & faithfulness of Python→WhyML lowering

**Status:** Draft specification (normative, implementation-agnostic)
**Version:** 1
**Source of requirements:** `07-0647-gaps.md` (R8–R13), from body-level verification of
`pure_lib/re/_engine.py`.
**Scope:** the *output contract* of PyCSL's source-to-WhyML lowering — the properties the
generated WhyML MUST satisfy for the underlying prover to accept and faithfully check it. This
document specifies **what must hold**, not **how** to achieve it; no file, function, symbol-naming
scheme, or data structure is prescribed.

Normative keywords: **MUST**, **MUST NOT**, **SHOULD**, **MAY** per RFC 2119.

---

## 0. Governing principle — the lowering's output contract

A correct lowering produces, for every accepted source program, WhyML that is (a) **well-formed**
(parses and type-checks in the target logic), (b) **self-contained** (depends on nothing it has
not declared or imported), and (c) **faithful** (its meaning is the meaning of the source — no
silently dropped operand, receiver, or type). The gaps R8–R13 are each a violation of one of
these three invariants. They are specified below as invariants the translator MUST uphold,
independent of the mechanism.

A lowering MUST NOT depend on the source being *written around* a limitation (renaming a class,
avoiding an operator, restructuring a call). Where a source construct cannot be lowered
faithfully, the translator MUST reject it with a diagnostic (a sound rejection), never emit
output that is ill-formed or that silently changes meaning.

---

## S1. Generated-name well-formedness and uniqueness — (covers R8, R9)

### S1.1 Reserved-name safety (R8)
Every identifier the lowering emits into the target logic MUST be a legal identifier of that
logic and MUST NOT coincide with any of the target's **reserved words**. The set of reserved
words is a property of the target logic, not of the source; the lowering MUST treat a source name
whose mechanical translation would land on a reserved word the same as any other name — i.e.
produce a distinct, legal symbol for it.
- **Failure prevented:** a source entity whose name maps onto a target keyword makes the emitted
  module unparseable.
- The disambiguation scheme (suffixing, prefixing, escaping, a reserved-name table) is **left
  unspecified** — only the invariant (no emitted identifier is reserved or illegal) is required.

### S1.2 Cross-entity name uniqueness (R9)
When two or more **distinct** target entities are derived from one source name (e.g. a type and a
separate value both originating from one class reference), the lowering MUST give them **distinct**
target identifiers. No two distinct declared symbols may share a name in the same scope.
- **Failure prevented:** a type declaration and an unrelated constant (or any two derived symbols)
  colliding on one name is a redeclaration / kind error.
- The naming/namespacing strategy that achieves uniqueness is **left unspecified**.

### S1.3 Stability (non-normative note)
Whatever scheme S1.1/S1.2 use SHOULD be deterministic (the same source yields the same names) so
output is reproducible; this supports byte-stable regression checks but is not itself a
correctness requirement.

---

## S2. Output self-containment — (covers R10)

### S2.1 Declared-before-used closure
The emitted WhyML MUST declare or import **everything it references**. For every theory, type,
operator, or symbol that appears in the output (in a body **or** in a specification/contract
formula), the corresponding import/declaration MUST be present in the module. In particular, when
the lowering emits a construct expressed in terms of a target-logic theory, it MUST also emit that
theory's import.
- **Failure prevented:** emitting a formula that uses a theory's symbols while omitting the
  theory's import yields an "unknown symbol / unbound" error — the module is not self-contained.
- This MUST hold uniformly whether the dependency is introduced by a body operation or by a
  contract clause (a specification that names a theory creates the same import obligation as a
  body that does).
- The import-tracking mechanism (eager, demand-driven, whole-module scan) is **left unspecified**;
  only closure of the used-set under declaration is required.

---

## S3. Method-receiver fidelity — (covers R11, R12)

### S3.1 Receiver presence (R11)
When an instance method is lowered to a target-level function, the **receiver** (the instance the
method is invoked on) MUST be present and in scope throughout the lowered body. Any reference in
the body to the receiver or its fields MUST resolve. The lowering MUST NOT produce a body that
mentions the receiver while the receiver is absent from the function's interface.
- **Failure prevented:** a method body referring to the instance (or its state) when the instance
  is not a parameter is an unbound-symbol error.

### S3.2 Receiver passing for every call form (R12)
For **every** method-call form — including a call on a *computed* receiver such as
`expr.method()` where `expr` is itself an indexing, attribute, or call result — the lowering MUST
pass the evaluated receiver to the lowered call. The receiver MUST NOT be dropped, and the lowered
call's result MUST remain connected to the actual receiver value.
- **Failure prevented:** lowering `expr.m()` to a receiver-less nullary operation severs the
  result from `expr`, so the proof reasons about an unrelated value — a *silent faithfulness*
  violation (the output type-checks but means something else), which is worse than a hard error.
- Chained and nested receiver expressions MUST be handled with the same fidelity as a simple
  variable receiver.

---

## S4. Type fidelity across declaration, body, and use — (covers R13)

### S4.1 Consistent value typing
A value's target type MUST be consistent everywhere it appears — a function's declared return
type MUST match the type its body actually produces, and an actual argument's type MUST match its
parameter. The lowering MUST NOT declare a value at one type while constructing or consuming it at
another.
- **Failure prevented:** declaring a function's result as one type while the body returns a
  different one (e.g. a structured value where a scalar is declared) is a type error that blocks
  body-level verification.

### S4.2 Faithful types for non-scalar values (no-more-int)
A value whose source type is non-scalar (a class instance, and likewise any composite) MUST be
given a faithful target type that preserves its structure — it MUST NOT be silently coerced to a
scalar placeholder. This is the same doctrine as the project's de-int-ification program: each
source type maps to its faithful target type class (record/variant for an instance), not to
`int`. A function that returns an instance therefore has an instance-typed result end-to-end.
- **Failure prevented:** modelling every value as a scalar makes instance construction and
  instance-typed returns ill-typed (and, where it does not error, unsound).
- The representation choice (a named record/variant per class, a boxed/allocated model, etc.) is
  **left unspecified**; only structure-preserving, internally-consistent typing is required.

---

## 5. Conformance

A conforming lowering satisfies, for every program it **accepts**:
- **C1 (well-formed):** the emitted WhyML parses and type-checks in the target logic — no reserved
  -word identifier (S1.1), no duplicate symbol (S1.2), no type mismatch (S4.1).
- **C2 (self-contained):** every referenced theory/symbol is declared or imported (S2.1).
- **C3 (faithful):** no receiver is dropped (S3), no value is silently retyped to a scalar (S4.2);
  the meaning of the output equals the meaning of the source.
- **C4 (sound rejection):** any source construct it cannot lower under C1–C3 is **rejected with a
  diagnostic**, never lowered to ill-formed or meaning-changed output.

Each invariant SHOULD be exercised by at least one body-level conformance case: a source program
that previously triggered the corresponding gap and now lowers to provable WhyML (or, for a
genuinely unsupported construct, is cleanly rejected per C4).

## 6. Out of scope (explicitly unspecified)

This specification deliberately fixes no mechanism. The following are implementation choices left
to the translator, constrained only by the invariants above: the reserved-name disambiguation
scheme; the cross-entity namespacing scheme; the import-tracking strategy; how the receiver is
threaded into lowered calls; the concrete representation of class instances (record, variant,
boxed integer with an allocation model); and the diagnostic wording for C4 rejections.

## 7. Traceability

| Req (07-0647-gaps.md) | Invariant | Class of violation |
|------------------------|-----------|--------------------|
| R8  reserved-word collision (`match`) | S1.1 | well-formedness |
| R9  type/constant name collision      | S1.2 | well-formedness |
| R10 missing theory import             | S2.1 | self-containment |
| R11 receiver (`self`) absent          | S3.1 | faithfulness (unbound) |
| R12 receiver dropped on `expr.m()`    | S3.2 | faithfulness (silent) |
| R13 class-return type mismatch        | S4.1 / S4.2 | type fidelity |
