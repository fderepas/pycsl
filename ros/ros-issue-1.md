# Bug Report: Duration/Time 64-bit Overflow at the C-Python Boundary

**Component:** `rclpy` — `duration.py`, `time.py`
**Severity:** High (safety-critical timing corruption)
**Threat category:** ros-report.md Threat #1 — Memory corruption at C-Python boundary
**Audited version:** rclpy rolling, tag `11.0.1`, commit `69d5ea9`

---

## Summary

Code review of the `Duration` and `Time` nanosecond arithmetic in `rclpy`
confirms that the **core int64 overflow guard is correct**: values outside
`[-2^63, 2^63)` are properly rejected with `OverflowError`. However, the
analysis uncovered **three issues at the boundaries** of the implementation
— areas where the Python code interacts with float conversion and ROS
message serialization — that can silently corrupt timing values in a
running ROS 2 system.

---

## Finding 1 — `to_msg()` silently overflows int32 for durations > 68 years

### Location

`duration.py` line 111:

```python
seconds, nanoseconds = divmod(self.nanoseconds, S_TO_NS)
return builtin_interfaces.msg.Duration(sec=seconds, nanosec=nanoseconds)
```

### Root cause

`Duration.__init__` accepts nanosecond values in the full int64 range
`[-2^63, 2^63)`, corresponding to ±292 years. But `to_msg()` decomposes
nanoseconds into a `(sec, nanosec)` pair for the
`builtin_interfaces/msg/Duration` ROS message, whose IDL declares:

```
int32 sec       # range: [-2,147,483,648 .. 2,147,483,647]
uint32 nanosec  # range: [0 .. 4,294,967,295]
```

For any `Duration` where `|nanoseconds| ≥ 2,147,483,648 × 10^9`
(≈ 2.1 × 10^18 ns ≈ **68 years**), `divmod` produces a `sec` value that
exceeds int32 range. The Python-to-C message serialization then silently
truncates or wraps the value.

### Proof of concept

```python
from rclpy.duration import Duration

d = Duration(nanoseconds=2_147_483_648_000_000_000)   # 68 years, valid int64
msg = d.to_msg()

# msg.sec is now 2,147,483,648 — exceeds int32_max (2,147,483,647)
# Depending on the DDS binding, this either:
#   a) wraps to -2,147,483,648  (silent corruption)
#   b) raises OverflowError     (at serialization, not at to_msg)
#   c) truncates silently

# Negative durations are worse:
d2 = Duration(nanoseconds=-9_223_372_036_854_775_808)  # min int64
msg2 = d2.to_msg()
# sec = -9,223,372,037  — far below int32_min
```

### Impact

**Note:** The autogenerated `builtin_interfaces.msg.Duration` message setter
may validate the int32 range at construction time, raising `AssertionError`
or `OverflowError`. Under default Python execution, the overflow is caught
at `to_msg()` rather than at `Duration.__init__()`, which is confusing but
not silently corrupt. However, under `python -O` (common in production),
assertion-based guards in the generated code are removed, and the overflow
IS silently corrupt. The core issue remains: the error surfaces at
serialization, not at creation, and disappears entirely under `-O`.

A corrupted `sec` field propagates through DDS serialization to other nodes.
For a safety-critical system (e.g., autonomous vehicle using ROS 2), a
deadline or liveliness timer constructed from a corrupted Duration could fire
at the wrong time or never fire, leading to:

- **Missed safety deadlines** — a watchdog timer that should expire in 100
  years (used as "infinite" by some frameworks) wraps to a short duration
- **Incorrect control loop timing** — a duration used for trajectory
  interpolation silently changes magnitude
- **Silent data corruption** — the bug is at serialization, not at creation,
  so no error is raised in the node that creates the Duration

### Recommendation

Add a range check in `to_msg()`:

```python
def to_msg(self) -> builtin_interfaces.msg.Duration:
    seconds, nanoseconds = divmod(self.nanoseconds, S_TO_NS)
    if seconds > 2147483647 or seconds < -2147483648:
        raise OverflowError(
            f'Duration seconds ({seconds}) exceeds int32 range for ROS message')
    return builtin_interfaces.msg.Duration(sec=seconds, nanosec=nanoseconds)
```

The same issue applies to `Time.to_msg()` at `time.py` line 166.

## Finding 2 — Float precision loss silently corrupts nanosecond values

### Location

`duration.py` line 32:

```python
total_nanoseconds = int(seconds * S_TO_NS)
```

`time.py` line 51:

```python
total_nanoseconds = int(seconds * S_TO_NS)
```

### Root cause

The `seconds` parameter is typed `Union[int, float]`. When a `float` is
passed, the multiplication `seconds * S_TO_NS` is performed in IEEE 754
double precision, which has only 53 bits of mantissa (≈ 15.9 significant
decimal digits). Nanosecond values above `2^53` (≈ 9.0 × 10^15 ns ≈
**104 days**) lose precision in the float multiplication.

### Proof of concept

```python
from rclpy.duration import Duration

# This value should produce INT64_MAX nanoseconds:
target_ns = 9223372036854775807   # 2^63 - 1
seconds_as_float = target_ns / 1e9   # 9223372036.854776

d = Duration(seconds=seconds_as_float)
# int(9223372036.854776 * 1e9) = 9,223,372,036,854,775,808 = 2^63
# This OVERFLOWS — OverflowError raised!
# But the caller intended a valid value (2^63 - 1), one nanosecond below max.
```

More subtly, for medium-scale values:

```python
# 10^18 + 1 nanoseconds (≈ 31.7 years)
target = 1_000_000_000_000_000_001
seconds_as_float = target / 1e9

d = Duration(seconds=seconds_as_float)
# int(1000000000.0000001 * 1e9) = 1,000,000,000,000,000,000 (off by 1 ns)
```

IEEE 754 double precision loses information starting at 2^53:

```
int(float(9007199254740993)) = 9007199254740992   # off by 1
```

### Impact

- **1-nanosecond timing errors** accumulate in long-running robotic systems
- Values near the int64 boundary are **unpredictably accepted or rejected**
  depending on float rounding direction
- The `float` path in `__mul__` (`int(self.nanoseconds * other)`) has the
  same problem for large nanosecond counts

### Recommendation

For integer callers, bypass the float multiplication:

```python
def __init__(self, *, seconds=0, nanoseconds=0):
    if isinstance(seconds, int) and isinstance(nanoseconds, int):
        total_nanoseconds = seconds * S_TO_NS + nanoseconds
    else:
        total_nanoseconds = int(seconds * S_TO_NS) + int(nanoseconds)
    ...
```

Consider also adding a warning when `seconds` is a float and the result
exceeds 2^53 nanoseconds.

## Finding 3 — `__add__` / `__sub__` overflow is caught but not documented

### Location

`duration.py` lines 52–60:

```python
def __add__(self, other: 'Duration') -> 'Duration':
    if isinstance(other, Duration):
        return Duration(nanoseconds=other.nanoseconds + self.nanoseconds)
    return NotImplemented
```

### Analysis

Code review confirms that this pattern is correct: the sum
`other.nanoseconds + self.nanoseconds` is computed in Python's arbitrary-
precision integers (no silent wraparound), and the resulting `Duration()`
constructor call applies the int64 range check. If the sum overflows, the
constructor raises `OverflowError`.

**This is the correct design** — all arithmetic is guarded by the constructor.

However, the exception is undocumented. A caller doing `d1 + d2` has no
indication that this can raise `OverflowError`. The same applies to `__sub__`
and `__mul__`.

### Recommendation

Add `:raises OverflowError:` to the docstrings of `__add__`, `__sub__`, and
`__mul__`.

## Affected versions

All versions of `rclpy` since the introduction of the `Duration` class.
The code structure has been stable since the initial ROS 2 release.

**Files:**
- `rclpy/rclpy/duration.py` — Findings 1, 2, 3
- `rclpy/rclpy/time.py` — Findings 1, 2 (same patterns)
- `rclpy/rclpy/constants.py` — defines `S_TO_NS = 10^9` (no issue)
