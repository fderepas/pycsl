# 1009 — PyCSL tool gaps blocking remaining proof obligations

## Context

After reaching 96.4% proven (3986/4134 VCs) on the pure `os` module backed by
`UnixInodeFileSystem`, the remaining ~148 failing VCs trace to two tool-level
gaps in PyCSL's stub generation for module-level helper functions and
`.encode()` calls. This document lists precise requirements for the PyCSL tool
to close these gaps.

---

## R1 — `assigns \nothing` on helper stubs must emit `writes {}`

**Current behavior:** Module-level helper functions (e.g., `_unpack_direntry`,
`_unpack_inode`, `_pack_direntry`) have `#@ assigns \nothing` in their Python
annotations. When PyCSL imports them as `val` stubs in the WhyML output, the
`assigns \nothing` is **not** translated to a `writes {}` clause.

**Example — current WhyML output:**
```whyml
val _unpack_direntry (data: array int) : (int, int)
    requires { (32 >= 0 && 32 <= Array.length data) }
    ensures  { true }
```

**Expected WhyML output:**
```whyml
val _unpack_direntry (data: array int) : (int, int)
    requires { (32 >= 0 && 32 <= Array.length data) }
    writes   { }
    ensures  { true }
```

**Impact:** Without `writes {}`, Why3 assumes the stub can modify any mutable
state in scope, including the module-level global `_filesystem`. After a call
to such a stub, the prover loses all non-invariant facts about
`_filesystem`'s fields. The type invariant re-establishes structural
properties (e.g., `Array.length _filesystem.disk >= 131072`), but any
intermediate facts derived from field values are lost.

**Scope:** All `val` stubs generated from imported helper functions that have
`#@ assigns \nothing`.

---

## R2 — `name.encode(...)` stub must have `ensures Array.length result >= N`

**Current behavior:** When the inliner encounters a call like
`name.encode('utf-8')`, it generates an abstract stub:

```whyml
val name_encode_1 (x0: int) : array int
```

No `ensures` clause is emitted, so the returned array has unknown length.

**Impact:** The result of `name_encode_1` is passed to `_pack_direntry` which
requires `\valid(name_bytes, 30)` (i.e., `Array.length name_bytes >= 30`).
Without a length guarantee on the encode result, this precondition is
unprovable. This affects every function that calls `_dir_write_entry` (which
passes an encoded name to `_pack_direntry`): `link`, `rename`, `mkdir`,
`makedirs`, `symlink`, `open`.

**Required fix:** PyCSL should emit a postcondition on `.encode()` stubs. Two
options:

- **Option A (conservative):** `ensures { Array.length result > 0 }` — always
  sound for `.encode()` on a non-empty string.
- **Option B (precise):** Derive the length from the string literal. If the
  encoded literal is known at compile time (e.g., `name` is a parameter of
  known max length, or the encode target is a field from a fixed-size struct),
  emit `ensures { Array.length result = N }`.

For the current `os` module, the minimum needed is
`ensures { Array.length result >= 30 }` for the name fields that feed into
`_pack_direntry`. This corresponds to the on-disk directory entry format
(`'>H30s'`).

**Note:** The same pattern applies to `target.encode('utf-8')` →
`target_encode_1` used in `symlink`.

---

## R3 — Tuple result postconditions: `ensures \result[N]` syntax

**Current behavior:** `_unpack_direntry` returns a tuple `(inode_num,
name_bytes)`. The annotation `#@ ensures \result[0] >= 0` should constrain
the first tuple element. Verify that PyCSL correctly translates this to:

```whyml
ensures { let (r0, r1) = result in r0 >= 0 }
```

If PyCSL does not support `\result[N]` indexing for tuple results, this is a
blocking gap — there is no other way to constrain individual components of a
tuple return value.

**Impact:** Without this, `_unpack_direntry`'s first element (`inode_num`) is
unconstrained, and the `_dir_lookup` loop invariant
`found >= 0 && found < 32` cannot be preserved after
`found := inode_num`.

---

## R4 — `assigns \nothing` should propagate through inlining

**Current behavior:** When a method body is inlined and it calls a helper
function with `#@ assigns \nothing`, the inlined call site should preserve
the `writes {}` semantics. Verify that the inliner does not strip or
reinterpret `assigns` annotations on callees within inlined bodies.

**Impact:** If `_dir_lookup` calls `_unpack_direntry` (assigns nothing),
and `_dir_lookup` is inlined into `stat`, `open`, etc., the
`_unpack_direntry` call in the inlined code must still have `writes {}`
in the WhyML output.
