# 1111-spec.md — specification for R5–R7 under the *no-more-int* doctrine

**Status:** Draft specification (normative) — revision 2 (faithful-types rewrite)
**Version:** 2
**Source of truth for requirements:** `1111.md` (R5, R6, R7), from `pure_lib_test/formal_0001.py`
**Supersedes:** revision 1, which solved R5 with a `str_to_int` int-coercion. **That approach is

Normative keywords: **MUST**, **MUST NOT**, **SHOULD**, **MAY** per RFC 2119.

## 0. Doctrine — *no-more-int* (the long-term investment)

PyCSL historically modelled every value as `int`. That is unsound-by-convenience: it makes
`"a" == "b"`, list aliasing, and float rounding indistinguishable from integer facts. An
ongoing program already replaces the int-model type-by-type with its faithful WhyML **type
class**:

| Python type | Faithful WhyML type class | Program stage (existing) |
|-------------|---------------------------|--------------------------|
| `int`, `bool` | `int` | (baseline — the ONLY type that stays `int`) |
| `float` | `real` | no-more-int **Stage D** |
| `str` | `string` (`string.String`) | **strings-plan** Stage 1–2 |
| `list`, `tuple` | `array int` / `seq int` | (arrays) |
| `bytes`, `bytearray` | `array int` (byte buffer) | partial — see `0442.md` B2 |
| `dict`, `set`, `frozenset` | `map 'k (option 'v)` | no-more-int **-3 A1** |
| class instance | record | no-more-int **-2 Track 3 / A6** |
| `#@ datatype` | Why3 variant | no-more-int **-3 A5a** |

**Governing rule (normative).** `int` is reserved for values whose Python type is genuinely
integral. Any value with a faithful type class above **MUST** be lowered to that class
end-to-end — through parameters, returns, module constants, defaults, **and cross-module stub
boundaries**. A new feature **MUST NOT** introduce a coercion (`str_to_int`, hash-to-int,
"model X as int") to bridge a faithful type into `int`; such a coercion is a regression of this
doctrine and is rejected at review.

R5, R6, R7 are three places where the int-model still leaks across the *import boundary*. They
are specified below as **completions of the no-more-int program**, not as int accommodations.

## R5 — string values keep type `string` across the import boundary

### R5.1 Root cause (corrected)
The caller's `filename: str` lowers (correctly) to WhyML `string` (strings-plan,
`functions.py::_param_type_str:33-36`). The imported `open` stub takes `filepath: int` **only
because the library source leaves `filepath` unannotated** (`pure_lib/os/__init__.py:261`,
`def open(filepath, flags, mode=0o777, …)`) and the cross-module signature defaults an
unannotated param to `int`. The defect is an **int leak in the stub signature**, not a missing
coercion in the caller.

### R5.2 Behaviour (normative)
1. **Cross-module stub signatures MUST carry the imported function's real declared parameter and
   return types** (`str`→`string`, `list`/`tuple`→`array int`, `dict`→`map …`, `float`→`real`,
   class→record, …), exactly as the function would be typed if defined locally. The import
   resolver **MUST NOT** collapse an annotated non-int parameter to `int`.
2. A `str` value passed to a `str` parameter **MUST** flow as `string` with **no coercion**.
   `str_to_int` (and any value→int hash bridge) **MUST NOT** be emitted. *(Revision-1 reversal.)*
3. String identity is **Why3 `string` equality**, not an int hash. Constants, comparisons, and
   `in`/concat use the string theory (already true for the language per strings-plan; this spec
   extends it to imported stub signatures).

### R5.3 Library obligation (faithful source, not a workaround)
A library parameter that denotes a string **MUST** be annotated `: str` in the source so its
stub is `string`-typed. Annotating `def open(filepath: str, …)` is the *correct* type, not a
deformation — it is required to make the source self-describing. (Contrast `comment.md`'s
rejected deformations, which *lied* about types; this *tells the truth* about them.)

### R5.4 WhyML encoding
Before (int leak):
```whyml
val open (filepath: int) (flags: int) (mode: int) : int    (* string caller → type error *)
```
After (faithful):
```whyml
val open (filepath: string) (flags: int) (mode: int) : int
…
open filename flags mode          (* filename : string → string param: no coercion *)
```

### R5.5 Edge cases
- Genuinely-int parameter (a flag, an fd) stays `int` — the doctrine does not string-ify ints.
- A `string` flowing into an `array int` (bytes) parameter is the `encode`/bytes path
  (`0442.md` A2/B2), governed by the bytes type class, never `str_to_int`.
- Mixed: `os.write(fd, data: list)` already annotates `data` — confirm `list`→`array int`
  propagates across the import the same way `str`→`string` must.

### R5.6 Acceptance
`pure_lib_test/formal_0001.py` proves with `filename: str` retained (no annotation drop, no
coercion), the `open` stub showing `(filepath: string)`. Conformance §6.R5.

## R6 — imported constants keep their real type *and* value

### R6.1 Behaviour (normative)
An imported compile-time constant **MUST** be bound to its literal value **at its faithful type
class**. For an integral constant (`SEEK_SET = 0`, `O_CREAT = 64`) the faithful type is `int`, so:
```whyml
let constant sEEK_SET : int = 0
```
A value-less `val constant sEEK_SET : int` (prover knows nothing) **MUST NOT** be emitted. If a
future imported constant is a `str`/`float`/etc., it **MUST** be bound at that type
(`let constant NAME : string = "…"`), consistent with §0 — R6 is type-class-general, not
int-special.

### R6.2 Mechanism
The defining module's literals are already collected (`collect_module_constants`,
`Module5_IREmitter:68-72`) and folded for a module's *own* constants
(`expressions.py:1470-1471`). Import resolution **MUST** propagate the imported module's
`{name: (type, value)}` map into the importer so the same fold/`let constant` path covers
imported names. Local definitions shadow imported ones deterministically.

### R6.3 Edge cases
- Non-literal / computed constants: not covered; keep current treatment (no spurious value).
- `O_CREAT | O_WRONLY` as a *constant*: folded only if compile-time evaluable; otherwise it is a
  call-site expression (R7), not a constant.

### R6.4 Acceptance
`lseek(fd, 0, SEEK_SET)` proves `0 <= how <= 2` with `SEEK_SET` imported; a negative driver
asserting `SEEK_SET == 1` is unprovable. Conformance §6.R6.

## R7 — default arguments filled at the call site, at the parameter's real type

### R7.1 Behaviour (normative)
When a cross-module call passes fewer positional args than the callee arity and the missing
trailing parameters have defaults, PyCSL **MUST** fill them from the callee's default IR
expressions (`Module5_IREmitter:461` already captures `{"default": …}`), producing a total
application. Partial application **MUST NOT** be emitted.

### R7.2 Type fidelity (the no-more-int tie-in)
Each filled default **MUST** be lowered at its parameter's **faithful type class** (§0): an
`int` default (`mode=0o777`) → `int` literal `511`; a `str` default → `string` literal; etc.
Default fill **composes with R5/R6** but introduces **no** int-coercion. Evaluate the default in
the **callee's** constant scope (so `mode=0o777` and constant-valued defaults resolve).

### R7.3 WhyML encoding
Before (partial application → type error):
```whyml
open filepath flags          (* 2 of 3 → int -> int *)
```
After (default `mode=0o777=511` filled at type `int`):
```whyml
open filepath flags 511
```

### R7.4 Errors
- Missing positional arg with **no** default → hard, descriptive error (never silent partial
  application).
- Keyword args / `*`-only params (note `open(…, *, dir_fd=None)`): out of scope; positional fill
  only. A keyword-only param with a default is simply omitted from the positional stub.

### R7.5 Acceptance
`open(filename, O_CREAT | O_WRONLY)` proves with `mode` defaulted. Conformance §6.R7.

## 8. Explicitly rejected (anti-doctrine)
- **`str_to_int` / any value→int coercion** (revision-1 R5): rejected — entrenches the int model.
- **Global `str`→`int`** (1111.md R5 option a): rejected — deletes the strings-plan.
- **Per-arity wrapper `val`s** (1111.md R7 option a): rejected — symbol proliferation.
- **Modelling string identity as an int hash** at the import boundary: rejected — string identity
  is Why3 `string` equality.

## 9. De-int-ification backlog (this spec's place in the larger program)
R5–R7 are import-boundary instances. Remaining int leaks to retire under §0 (track alongside
`0442.md`):
- **Bytes/list unification** — `_symtype_to_whyml` drops `bytes`→`int` (`0442.md` B2); should be
  `array int`. Blocks the faithful `-> bytes` stub signatures (`comment.md` D1).
- **String-hash constants** — module-constant string values currently fold to an int hash; should
  be `string` literals once R6 generalises to the string type class.
- **Record array-field reads** (`0442.md` B1) — orthogonal but same EXTREME RIGOR program.
- **Library annotation sweep** — audit `pure_lib/*` for unannotated string/list/dict params (like
  `open(filepath)`) and annotate them to their real types so every stub signature is faithful.
