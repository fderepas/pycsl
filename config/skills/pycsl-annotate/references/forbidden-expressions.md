# Forbidden in Contract Expressions

These rules apply only inside `#@` expressions (`requires`, `ensures`, `loop invariant`, `class invariant`):

- **NEVER use arbitrary function calls** (e.g., `abs(x)`, `range(x)`, `len(x)`) inside `#@` expressions. The contract parser does not support them.
- **Exception — `\length(arr)`** (backslash prefix, no space): the only supported function-like atom. Use this to refer to an array parameter's length. Example: `#@ requires \length(arr) >= n`.
- **Exception — `\is_sorted(arr, lo, hi)`**: true iff `arr[lo..hi)` is sorted ascending (pairwise adjacent: `arr[k] <= arr[k+1]` for all `lo <= k < hi-1`). Use in `requires`/`ensures`/`loop invariant`. Example: `#@ ensures \is_sorted(arr, 0, n)`.
- **Exception — `\sum(arr, lo, hi)`**: sum of elements `arr[lo..hi)`. Auto-generates a recursive logic function with a snoc lemma for loop invariant proofs. Example: `#@ ensures \result == \sum(arr, 0, n)`.
- **Exception — Pure function calls**: a function with `#@ assigns \nothing` (pure) can be called in contracts. Example: `#@ ensures \result == abs_val(a) + abs_val(b)` where `abs_val` is defined with `#@ assigns \nothing`.
- **Exception — `arr[i]`**: array subscript reads are supported inside contract expressions (e.g., inside `\forall` bodies).
- **`dict`-typed parameters** are modeled as `array int` (same as `list`). Use `\length(d)`, `d[k]`, `\is_sorted`, `\sum` on `dict` parameters the same way as on `list` parameters.
- **`True`, `False`, `None` ARE supported** as first-class atoms in `#@` expressions (annotations.md §3.1.18, §3.1.19). `True` is the recommended form for vacuous preconditions / postconditions — prefer it over the older `1 == 1` idiom (still accepted for backward compatibility). Use `False` over `0 == 1` for intentionally-unprovable postconditions. `None` maps to `0` in WhyML.
- **`%` (modulo) and `//` (floor-division) ARE allowed** in contracts. They map to WhyML `mod` and `div` respectively. `//` is emitted as prefix `(div l r)` via `int.EuclideanDivision`. Confirmed by test 0334 and `references/transpiler-limits.md` §7.
- **NEVER place blank lines between a `#@` block and the `def` or `class` keyword it annotates.** Blank lines cause libcst line-number mismatch and silently drop all contracts.
- **String literals are supported.** Double-quoted strings map to WhyML's `string` type. Example: `#@ ensures \result == "hello"`.
- **Length captured in a local variable**: when a loop invariant or variant needs the length of a collection, either use `\length(arr)` directly (for array parameters) or assign `n = len(collection)` **before** the loop in the Python body and reference `n` in all loop contracts.
- **NEVER compare an integer parameter to a string literal** in a contract expression. For example, `#@ requires event_len != ""` is wrong when `event_len` is an `int`. Use integer comparisons such as `#@ requires event_len > 0` or `#@ requires event_len >= 0`.
- **NEVER write a bare identifier as the full `requires` expression** (e.g., `#@ requires event_len`). Every `requires` expression must contain a comparison operator. Use `#@ requires event_len > 0` or a similar inequality.
- **NEVER use chained comparisons** (e.g., `#@ ensures \result == 1 == 1`, `#@ ensures len(\result) <= 1 == 1`, `#@ ensures \result < 1 == 1`). The PyCSL grammar does not support Python-style chained comparisons, including mixed-operator forms like `<= N == M`, `>= N == M`, `< N == M`, or `> N == M`. Use a single comparison such as `#@ ensures True` or `#@ ensures \result >= 0`. Note: `\result` is a scalar integer — `len(\result)` is meaningless and will cause a parse error; never write `len(\result)` in any contract.
- **Functions returning collections (dict, set, list, or any non-integer type)** — e.g., `word_frequencies`, `unique_sorted_values`, or any function whose return type is `dict`, `set`, or `list` — cannot express a scalar postcondition on the collection itself. Do NOT write `#@ ensures len(\result) ...` (forbidden function call) or any chained comparison. Use `#@ ensures True` for the postcondition of such functions.
- **Functions that perform subscript assignment on a `dict`-typed variable** (e.g., `counts[word] = counts.get(word, 0) + 1` or `indexed[key] = value` where `indexed: dict = {}`) cannot be verified in the hoare model — PyCSL only permits subscript assignments on `list`-typed variables. Add `#@ \trusted` immediately before the `def` keyword (keeping all other contracts: `requires`, `ensures`, `assigns`) so the body is assumed correct without verification.
- **NEVER use `#@ \trusted` on user-defined functions** unless (a) the function performs dict subscript assignment (see above), or (b) the function operates exclusively on external library types that cannot be modelled in WhyML (e.g., `libcst.CSTNode`, `lark.Transformer`, file handles, sockets, database cursors). `\trusted` means the body is not verified — the solver blindly assumes the contracts hold. It is reserved for library stubs in `src/pycsl_lib/` (where no source is available), dict-manipulating functions (where PyCSL cannot model the heap), and library-wrapping code (where the types involved have no WhyML representation). Using `\trusted` on a normal function that operates on modelable types (int, list, simple classes) defeats the purpose of formal verification. If a proof fails, fix the contracts or invariants instead of marking the function trusted.
- **NEVER leave `\old(` unclosed** (e.g., `#@ ensures \result == \old(1 == 1`). Every `\old(` must have a matching `)`. A malformed `\old(` expression will be removed entirely by the post-processing guards.
- **NEVER use an arbitrary variable name as an `assigns` target** unless that variable is actually a global or mutable parameter being modified by the function. For pure functions that modify no external state, use `#@ assigns \nothing`. Names like `log`, `count`, `result`, etc. are not valid `assigns` targets unless they are declared as globals or class fields.
- **NEVER name a function parameter or local variable `val`** — `val` is a reserved keyword in WhyML (it introduces spec-only declarations). If a parameter named `val` reaches the transpiler, the emitted body will reference the undefined name `val` (e.g., `arr[!i] <- val`) and Why3 will fail with a syntax error. Use `v`, `value`, or any other descriptive name instead. The annotation agent renames `val` parameters automatically, but prefer a non-reserved name from the start.
- **NEVER name a local variable `match`** — `match` is a reserved keyword in WhyML (it introduces pattern-matching expressions). If a local variable named `match` is used (e.g., `match = 1` as a boolean flag), Why3 will fail with a syntax error at the emitted `let match = ref 1 in`. Use `is_match`, `found`, or any other descriptive name instead. The annotation agent renames `match` local variables to `is_match` automatically, but prefer a non-reserved name from the start.
- **NEVER use a variable name in a `loop invariant` that does not exist in the function body.** Always inspect the actual Python code and use the exact variable names present — e.g., if the accumulator is `acc`, write `#@ loop invariant acc == 0 or acc == 1`, NOT `#@ loop invariant result == 0 or result == 1`. Substituting a generic name like `result` for a real local variable (`acc`, `total`, `found`, etc.) will cause the WhyML transpiler to fail with an unbound variable error. **Important:** the annotation pipeline renames any local variable called `result` to `acc` (to avoid shadowing Why3's `result` binding in postconditions). Therefore, if the Python source uses a local variable named `result` (e.g., `result = arr[0]` in `array_max` or `array_min`), the annotated output will use `acc` in the body — and every `#@ loop invariant` that tracks that accumulator must also use `acc`, not `result`. Example: `#@ loop invariant acc >= arr[0]`, NOT `#@ loop invariant result >= arr[0]`.
- **NEVER write `#@ ensures \result >= 1` for a function that returns `len(collection)` (or `length log`, `length arr`, etc.) without an explicit precondition that guarantees the collection is non-empty.** `len()` always returns ≥ 0; without a `#@ requires \length(log) >= 1` (or equivalent), the solver cannot prove `result >= 1` and will time out. Use `#@ ensures \result >= 0` unless the non-empty precondition is present.
- **NEVER write `#@ ensures \result == \old(\length(arr)) + 1` (or any variant claiming the result equals the old length plus one) unless the function body actually appends an element to `arr`.** If the function only reads the collection and returns its current length (e.g., `return len(log)`), then `result == old_length` holds — not `result == old_length + 1`. Adding the `+1` postcondition creates a contradictory contract that can never be discharged. Only use `\result == \old(\length(arr)) + 1` when the function body actually appends exactly one element before returning the new length.
- **NEVER implement array/list traversal functions (e.g., `sum_list`, any function that iterates over all elements of an array/list parameter) using recursion with slice notation** (e.g., `values[1:]`). The hoare model transpiler does not support slice notation, and passing `values[0]` (an `int` element) as the array argument is a type error that will cause WhyML compilation to fail. Always rewrite such functions as iterative loops: capture `n = len(values)` before the loop, then use `i = 0` / `while i < n: ... i += 1` with `#@ loop invariant 0 <= i and i <= n` and `#@ loop variant n - i`. Do NOT add a function-level `#@ \variant` — that belongs only on genuinely recursive functions. See Example 8 for the canonical pattern.
- **NEVER use `\length(arr) >= 0`** for any array parameter — array length is trivially non-negative and this precondition adds no useful constraint. Use `#@ requires True` instead.
- **When an explicit integer parameter `n` is used as the upper-bound of a `while i < n:` loop that accesses `arr[i]` (where `arr` is a `list` parameter), always add both `#@ requires n >= 0` and `#@ requires n <= \length(arr)`.** Without `n >= 0`, the solver cannot establish `0 <= n` at loop initialization (the `!i <= !n` invariant fails for the base case). Without `n <= \length(arr)`, the solver cannot discharge the `Index in array bounds` sub-goal for `arr[!i]`. Do NOT use `#@ requires True` as the sole precondition for such functions — it is a placeholder that conveys no constraint. The postcondition for a sum over arbitrary integers is still `#@ ensures True` (elements may be negative, so the sum is not bounded below by 1 or even 0). See Example 8b for the canonical pattern.
- **NEVER use `\length(self.<attr>)` inside any contract clause** (loop invariant, requires, ensures). The PyCSL parser does not support dot notation inside `\length()`. If you need to assert something about the size of a collection attribute, use `#@ loop invariant True` or omit the invariant entirely.
- **NEVER use `\length(param)` when `param` is typed `str`.** `\length()` is only valid for `list`/array-typed parameters. Applying it to a `str` parameter compiles to `length event` in WhyML where `event` has type `string`, causing a fatal type error (`string vs array`). If you need to assert a string is non-empty, use `#@ requires True` (no direct equivalent in the hoare model).
- **NEVER use `\length(\result)` in any contract clause.** `\result` is a scalar integer return value — it is not an array, so `\length(\result)` has no meaning in the PyCSL grammar and will cause a parse or type error. If you need a postcondition for a function that returns an `int`, use `#@ ensures \result >= 0` or `#@ ensures True`.
- **NEVER write an implication postcondition (`==>`) in any `#@ ensures` clause for functions that use an index loop**, regardless of whether the left-hand side uses `\length(values)` (e.g. `#@ ensures \length(values) == 0 ==> \result == 0`) or a local variable (e.g. `#@ ensures n == 0 ==> \result == 0`). After the loop exits, the solver knows `!i = !n` but cannot chain back to `length values` or relate `n` to the accumulator, so the implication is never discharged and the proof times out (30 s, 42 M steps). For list-summation functions (or any function that traverses all elements via an index loop), use `#@ ensures True`. See Example 8. The annotation guard in `agent-annotate.py` enforces this by replacing any `#@ ensures` line that contains `==>` with `#@ ensures True`.
- **NEVER assign an array parameter to a local variable using `acc = values[0]` or slice-copy notation `acc = values[:]`.** `values[0]` is a scalar `int` element — assigning it to `acc` makes `acc` a `ref int`, so `n = len(acc)` and `acc[j]` subscripts are invalid and produce a WhyML type error. `values[:]` is treated as a slice and converted to `values[0]` by the transpiler guards, causing the same error. For in-place operations (e.g., `insertion_sort`), assign the whole array directly: `acc = values`.
- **Functions that return an array value — whether a sorted/modified parameter (e.g., `insertion_sort` assigns `acc = values` and returns `acc`) or a newly created internal array (e.g., `kmp_build_failure` builds a failure table `failure = [0] * m` and returns it) — MUST use `-> list` as the return type annotation**, NOT `-> int`. With `-> list`, Module 6 emits `: array int` as the WhyML return type, which matches the `array int` body result. Using `-> int` causes a fatal type mismatch because the body yields an `array int` but the signature declares `int`. Use `#@ ensures True` for the postcondition since the collection itself cannot be compared with a scalar.
- **When a function operates on string parameters character-by-character** (e.g., KMP or naive string-search, which call `len(text)` and access `text[i]`, `pattern[j]`) **annotate those parameters with type `list` instead of `str`**. In the hoare model, `str` parameters are automatically mapped to `array int` by Module 6, making `length text` and `text[i]` valid; but using `list` explicitly makes the intent clear and avoids any ambiguity. Never annotate such parameters as `str` when the function body performs subscript indexing on them, because `str` maps to WhyML's `string` type which does not support array subscript syntax.
- **For boolean-flag functions that return 0 or 1** (e.g., `is_sorted_non_decreasing` which sets `acc = 0` or `acc = 1` and returns `acc`), the postcondition MUST be `#@ ensures \result == 0 or \result == 1` — never just `#@ ensures \result == 0`, never `#@ ensures True`, and **never** `#@ ensures \result == 1 or \result == 0`. The disjunction **must always list 0 first**: `\result == 0 or \result == 1`. Reversed order (`\result == 1 or \result == 0`) causes a 30 s timeout because the prover discharges `result=0` first (via the `acc==0` branch) then `result=1`; the reversed form breaks that discharge order. This applies regardless of whether `acc` starts at `0` (e.g., `any_negative`) or `1` (e.g., `all_positive`, `none_zero`). See Examples 10, 11, and 12.
- **NEVER use `return <value>` inside an `if then` branch within a `while` loop body.** Module6 emits the `then` branch as a WhyML `int` expression (the constant) while the `else`/continuation branch is `unit` (an assignment), producing a fatal type mismatch (`This expression has type (), but is expected to have type int`). Instead use the **flag + sentinel** pattern: introduce `acc = <default>` before the loop, replace `return val` with `acc = val` followed by `i = n` (to force loop exit), convert the remaining loop body into an explicit `else:` branch with the index increment, then `return acc` after the loop. **Critically, you MUST also change the final `return True` / `return False` / `return 1` after the loop to `return acc`** — forgetting this causes the WhyML body to end with a constant `1` instead of `!acc`, making the early-exit assignment ineffective. See Example 10 for the canonical implementation of this pattern.

- **NEVER write `i = len` (bare function name) as the loop-exit sentinel.** The sentinel `i = n` in the flag+sentinel pattern refers to a concrete integer variable, NOT the built-in `len` function. Always capture the array length as `n = len(arr)` before the loop and write `i = n` — or write `i = len(arr)` (a call) if you do not introduce `n`. Writing `i = len` emits `i := len` in WhyML where `len` is an unresolved symbol, causing a Why3 type error. Example: `n = len(arr)` → `while i < n:` → `i = n` as sentinel.

- **NEVER use a bare boolean-flag variable as a condition** in `if`, `elif`, or `while` statements. Variables assigned `True`, `False`, `0`, or `1` are emitted by Module5 as integer IR nodes (`Number(1)` / `Number(0)`) and by Module6 as `ref int`, so `if is_match:` or `while j < m and is_match:` produces a WhyML type error: "This expression has type int, but is expected to have type bool". Always write an explicit comparison: `if is_match != 0:`, `while j < m and is_match != 0:`, and `if is_match == 0:` for the negated form. This applies whether the flag is initialised with a Python boolean (`is_match = True`) or an integer literal (`is_match = 1`). The annotation guard in `agent-annotate.py` auto-converts bare boolean flag conditions for both forms, but prefer writing the explicit form from the start.

- **NEVER emit duplicate `#@ requires`, `#@ ensures`, or `#@ assigns` lines for the same function.** Each contract clause must appear exactly once in the annotation block immediately preceding the `def`. Emitting the same `#@ requires n >= 0` twice (or any other clause) causes the transpiler to emit duplicate `requires`/`ensures` clauses in WhyML, making contracts harder to read and potentially causing unexpected solver behaviour.

- **NEVER declare `n: int` as a function parameter AND assign `n = len(arr)` in the function body.** When the IR emitter sees `n = len(arr)` as an assignment in the body, it treats `n` as a local variable (a `ref`) and drops it from the WhyML function's parameter list. Any `#@ requires` clause that references `n` (e.g., `#@ requires n >= 0`, `#@ requires n <= \length(arr)`) will then fail with an unbound variable error in Why3. Choose one of two consistent patterns: **(a) explicit bound parameter** — keep `n: int` in the signature, write `#@ requires n >= 0` and `#@ requires n <= \length(arr)`, and do NOT assign `n = len(arr)` in the body (the loop reads `n` directly from the parameter, as in `any_negative` and `none_zero`); or **(b) locally captured length** — omit `n` from the signature, capture `n = len(arr)` as the first statement of the body, use `\length(arr)` in function-level `requires` if needed, and use `n` only in loop invariants/variants. Option (a) is preferred for consistency with other parametric functions.

- **NEVER write a recursive function (one that calls itself by name) without `#@ \variant <param>` in its contract block.** Without this annotation PyCSL emits `let rec f` but no `variant { param }` clause in WhyML, and Why3 will time out on the termination sub-goal. Always place `#@ \variant <param>` immediately before the `def` line, after `#@ assigns`. The variant expression must be the parameter that strictly decreases toward the base case (e.g., `n` for `def factorial(n)`). See Example 7b.
- **NEVER leave a `#@ ensures` clause with an incomplete right-hand side** (e.g., `#@ ensures self._field ==` is malformed — it must always have a complete, parseable expression). When a method body assigns a constant to a field (e.g., `self._current_class = -1`), the postcondition MUST name that value explicitly: `#@ ensures self._current_class == -1`. Truncated `ensures` expressions produce parse errors or are silently dropped by the transpiler.
- **NEVER reference fields of external library types (e.g., LibCST nodes) inside `#@` contract expressions.** Methods that accept parameters of types imported from external libraries — such as LibCST's `cst.Module`, `cst.CSTNode`, `cst.SimpleStatementLine`, or any class defined outside the current Python file — iterate over fields (e.g., `node.header`, `node.leading_lines`, `line.comment`) that have no WhyML representation. The PyCSL pipeline defaults these parameters to type `int`, so any field access in a contract (e.g., `node.header`) produces an `unbound function or predicate symbol` error in Why3. For all methods whose parameter types come from an external library, use only trivial contracts: `#@ requires True`, `#@ ensures True`, and `#@ assigns \nothing`. Do NOT attempt to express any property involving the external node's fields.
- **NEVER access fields of external library type parameters in function bodies either.** The same `int`-mapping applies inside the function body: a body statement such as `n = len(node.header)` compiles to `let n = ref (length node.header)` in WhyML, where `node` has type `int`, causing the same `unbound function or predicate symbol 'header'` error as in a contract. For every method whose parameters come from an external library (e.g., a LibCST visitor method like `visit_Module(self, node)` or `visit_SimpleStatementLine(self, node)`), replace every body-level field access with a local `int` constant — e.g., replace `n = len(node.header)` with `n: int = 0`, replace `node.leading_lines[i]` with `0`, and replace `line.comment` with `0`. If the entire body consists of such external-field accesses with no verifiable integer logic, remove all body statements and use `pass` so the function compiles to a trivially provable no-op.
- **NEVER use `#@ requires True` as the precondition for a method that adds an integer parameter to a field guarded by a class invariant.** When the class has `#@ class invariant self._field >= 0` and the method body does `self._field += amount` (or `self._field = self._field + amount`), using `#@ requires True` leaves `amount` unconstrained. The solver cannot guarantee `self._field + amount >= 0` after the assignment, so the Type invariant sub-goal is marked Unknown. You MUST write `#@ requires amount >= 0` instead. Similarly, any parameter that is added to (or subtracted from) an invariant-guarded field must have the corresponding constraint: e.g., `#@ requires amount <= self._field` for a `withdraw`-style method on a `_field >= 0` class.
- **NEVER add `#@ \variant <param>` to a function that does not call itself by name.** A function that delegates to a helper (e.g., `kmp_search` calls `kmp_build_failure`) is not self-recursive and must NOT have a `#@ \variant` clause. Adding `#@ \variant arr` where `arr` is a `list`/`str` parameter emits `variant { arr }` in WhyML, but `array int` has no default well-founded ordering and Why3 rejects it with a type error. Only add `#@ \variant` to functions whose own body calls them by name (truly self-recursive).
- **NEVER write `\length(param)` inside an arithmetic sub-expression of `#@ ensures`** (e.g., `#@ ensures 1 == 1 - \length(pattern)` or `#@ ensures \result == n + \length(arr)`). Such expressions are mathematically false when the collection is non-empty and will always fail to verify. The only valid use of `\length(param)` in an `ensures` clause is as a standalone comparison operand: `#@ ensures \result == \length(arr)`, `#@ ensures \result >= \length(arr)`. If no useful postcondition involving collection length is provable, use `#@ ensures True`.
- **In two-pointer loops, use the loop's own bound variable in the upper-bound invariant.** When a loop is `while i < n:` with variant `n - i` (where `n = len(text)`), write `#@ loop invariant i <= n` — NOT `#@ loop invariant i <= m` (where `m = len(pattern)` is a different variable). Confusing `n` with `m` makes the bound wrong and the solver cannot prove the array-bounds VC for `text[i]`.
- **When a loop invariant asserts `m >= 1` (where `m = len(pattern)` is assigned before the loop), add `#@ requires \length(pattern) >= 1` as a function precondition.** Without this precondition the solver cannot establish `m >= 1` at loop initialization because `len(pattern)` could be 0. This applies to any function (e.g., `count_occurrences`) that iterates `while i <= n - m` and uses `m >= 1` as a loop invariant.
- **In KMP-style failure-table loops, add `#@ loop invariant k < m` wherever the body accesses `pattern[k]`.** The invariant `k >= 0` alone is insufficient — the solver needs the explicit upper bound `k < m` to discharge the array-bounds sub-goal for `pattern[k]`. This applies to both the outer loop and the inner `while k > 0:` loop in `kmp_build_failure`. See Example 13.
