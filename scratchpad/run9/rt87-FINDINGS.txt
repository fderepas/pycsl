KEY FINDING 1 (a1, false proof at head, PRE-EXISTING): u76's PYCSL-FUNCTION-FRAME is ROOT-granular, while the
importer's `val` frame is FIELD-granular.
- `_info316["declared"]` keeps only the ROOT of each `assigns` target (Module6_WhyMLTranspiler.py: "declared frame:
  roots of `assigns` targets"). So `#@ assigns r.a` puts r in `declared`, and a body write to r.b is never
  `undeclared`. The new check in functions.py therefore cannot fire.
- The importer emits `val f (r: r) : int ... writes { r.a }` (c/h/a1/x_a1.mlw), and the caller keeps r.b = 0.
- The owner's `let f` has NO `writes` clause (c/h/a1/o_a1.mlw), so Why3 infers the r.b write and the owner proves.
- CPython 5, both units P on both trees (c/{h,b}/a1/{o,x}_a1.log). With --deep the importer emission is identical (a1d).
- Methods are safe here because their `let` carries `ensures self.b = old self.b` for every field the frame does not
  name (a13 NP). Module functions get no such clause.
Fix direction (either one):
- (a) emit the declared frame on the owner's `let` as `writes { r.a }`, so Why3 rejects the undeclared r.b store at
  type-check;
- (b) make `declared` / `undeclared` field-granular for record parameters, the way the method path's field ensures
  already are.

KEY FINDING 2 (d1b, s1, false proofs at head, PRE-EXISTING): the #634 dict / set twin is still open.
- The parameter seeding in transpile skips dict / set parameters ("governed by WL-05 / route #244"). The refusal also
  removes `_func_mutated_collection_params` from `_u316` (the `_x316` exclusion).
- The owner's let gets `writes { d }`, honest in Why3, so it proves.
- The importer's `val f (d: ref (map string (option int)))` has NO `writes` because the declared frame is `assigns
  \nothing`. The caller keeps d["k"] = 0.
- d1 fails closed only by accident: the importer's own `writes { d }` is then unused, which is a type error. One write
  of the caller's own (d1b) removes the accident.
- Logs: c/{h,b}/d1b/*.log, c/{h,b}/s1/*.log.
Fix direction: for a function with `assigns`, refuse when a dict / set parameter is in the function's
`_func_mutated_collection_params` and is not named in the frame. Or always give the importer's val
`writes { d }` from the body measurement.

KEY FINDING 4 (b1, INTRODUCED path, reporting gap): a float field wrapped by the u76 carrier reaches a PyVal compare,
and `--soundness-report` does NOT list FLOAT-FINITE.
- The u76 carrier yields `HFloat x` for a value that may be a NaN, and `hval_eq` is reflexive. So
  `d["a"] == d["a"]` PROVES (head P), while CPython gives False for R(nan). At L21 the same program fails L3-tc.
- This relies on the declared FLOAT-FINITE assumption, and `--strict-float-finite` refuses it (b1s, R606). So it is
  not a false proof under the declared model.
- But the head soundness report (c/h/b1s/o_b1s.q.log) lists only BUILTIN-EXACT and LATIN1-STR, so the reliance is
  invisible in the default mode. The cause is in pycsl.py. `_ma_pv` looks for the string "PyVal" in symbol_table /
  param_annotations, and finds none: the annotation `Dict[str, PyVal]` with `PyVal = Any` is not recorded under that
  name. `_ma_fields` sees `float` only on a FieldGet that is an operand of the comparison, and here the field is read
  inside the dict literal.
- The equivalent float-PARAM program (b1q) fails L3-tc on both trees (`HInt x` with x: real). So this NaN-able path
  into HFloat is new with u74 / u76.
Fix direction: count a function as "holding a PyVal value" when its body hits the u76 float-field arm. Or report
FLOAT-FINITE for any function whose dict literal holds a float field.
