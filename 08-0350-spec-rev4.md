# 08-0350-spec-rev4 — `astmod` contracts **and** the parser family (P5), with explicit agent ownership

**Date:** 2026-06-08
**Status:** Draft (rev. 4)
**Supersedes:** `08-0350-spec-rev3.md`, rev2, rev1, `ast-req.md`
**Scope:** (a) bucketed `astmod` contracts for verifying **user code that imports `ast`**; (b) the
`07-1839` P5 parser family (`exec`/`eval`/`compile`/`ast.parse`/`literal_eval`), unified by the fact
that CPython runs them through **one** front-end. A *string argument* is either a **compile-time
constant** (parseable at verification time) or **dynamic** (unknowable → conservative havoc/`\trusted`).

**Revision 4 — what changed from rev3.** No technical/soundness change; rev3's four constant-source
fixes stand (splice soundness rests on the whitelist; faithful vs Modelled-rel-TCB; constant `eval`
narrowed to the closed fragment; spliced loops deferred to P5e). rev4 makes **ownership explicit**:
the work is split across **two agents**, and every section, gap, phase, and acceptance row is now
tagged with its owner, plus a §0 division-of-labor and a cross-agent dependency/handoff graph.

## 1  Context  *(shared)*

The PyCSL toolchain contains a 3,775-line pure-Python reimplementation of the stdlib `ast` module
(`src/pycsl/pure_ast.py`). Every pipeline stage imports it:

| Consumer | Key functions used |
|---|---|
| Module1_Ingestor | `parse`, `comments`, `walk`, `iter_child_nodes` |
| Module3_Weaver | `parse`, `walk`, `iter_child_nodes`, `NodeVisitor`, `unparse`, `literal_eval` |
| Module4_SemanticAnalyzer | `NodeVisitor`, `walk`, `iter_child_nodes` |
| Module5_IREmitter | `NodeVisitor`, `walk`, `iter_child_nodes`, `get_docstring`, `unparse`, `literal_eval` |
| import_classifier, pycsl.py, ConcurrencyChecker | `parse`, `walk`, `iter_child_nodes`, `dump` |

`pure_lib/astmod/__init__.py` is currently a stub: every node an opaque non-negative `int` handle,
every function a trivial body. So user code that imports `ast` verifies only up to type compatibility.

**The irony, named and resolved.** `pure_ast.py` is the parser the toolchain *itself* runs, so
`astmod` is a contract for PyCSL's own front-end. That tempts *self-verifying* the parser. **This spec
does not pursue that** (§2). The parser stays TCB; `astmod` over-approximates it solely so *user*
programs calling `ast` can be verified.

**One front-end, two surfaces.** `ast.parse(s)` is the *data* surface; `exec`/`eval`/`compile(s)` the
*executable* surface of the **same** parser; `literal_eval(s)` the restricted-evaluator surface. The
verdict on a *constant* `s` must be the same for all (§8.2).

## 2  Goal — and explicit non-goal  *(shared)*

**Goal (a) [STDLIB-facing]: let user code that imports `ast` verify against meaningful
postconditions** — not just `>= 0`. A verified user program may rely on:

1. The **faithful** identity/projection facts (§4.1).
2. **Referential transparency** of the pure helpers (`parse`/`dump`/`unparse` carry `assigns
   \nothing` → RT inference makes them pure; `dump(parse(s))` equal on equal `s`). *Determinism-via-
   purity*, not a claim about *which* string (§9).
3. Eventually (Phase 2–3), **`isinstance` dispatch on node types**, once nodes carry a real `τ`.

**Goal (b) [TOOL-facing] — P5: a sound, unified model of the parser family** so user code using it
verifies — *faithfully* on a constant source, *conservatively* (havoc + `\trusted`) on a dynamic
source — same verdict for the same string across the family.

**Non-goal: self-verification of `pure_ast.py`.** Contracts *over-approximate* the parser; a green
`astmod` test proves facts about the *contract*, not the 3,775-line body (TCB). Nothing narrows that TCB.

## 3  Classification lens (modelled / specified / stubbed + knowability)  *(shared)*

Every function is bucketed; **coverage is reported per bucket**:

- **Modelled** — faithful contract preserving real semantics (a real proof).
- **Specified** — axiomatized contract trusted as written; enters the TCB; sound only for the stated
  property.
- **Stubbed** — signature/handle only; proves nothing about the value.

P5 adds an orthogonal **knowability** axis (constant vs dynamic) that can *promote* a stubbed function
on a constant argument, to one of two grades:

- **Modelled (faithful)** — not parser-contestable (`literal_eval` of a literal; closed pure-constant
  `eval`). Trivial grammar ⇒ negligible parser-agreement assumption.
- **Modelled-relative-to-TCB** — depends on the *structure the parser produces* (`ast.parse`/`compile`
  of arbitrary source). Faithful **only if** the tool parser agrees with CPython — a named TCB
  assumption (§9), not a proof.

### 4.4  Soundness fix — `literal_eval` (split by knowability)  **[STDLIB]** dynamic / **[TOOL]** constant

The earlier `ensures \result >= 0` "for numeric literals" is **unsound** (`literal_eval("-5") == -5`).

- **Dynamic argument → honestly stubbed [STDLIB].** Non-constant `s` → unconstrained handle (no `>= 0`).
- **Constant argument → Modelled (faithful) [TOOL §8.3].** `literal_eval("[1,2]")`, `literal_eval("-5")`
  are evaluated at verification time to the *actual* value with true `τ`. Faithful (trivial grammar).

## 5  Node type classes (`_NODE_SPEC`) and `isinstance`  **[SEAM]**

`pure_ast.py` generates ~90 node classes; user code relies on `isinstance(node, ast.FunctionDef)`.

- **Mechanism [TOOL], landed:** `isinstance` lowers to `\subtag(\typeof(node), FunctionDef_tag)`
  (`07-1839` §4.2 / P4) — **not** `\in_globals` (a category error). This is the tool's; it exists today.
- **Node classes [STDLIB], Phase 2:** `\typeof` is decided only when the node carries a concrete `τ`.
  Today `parse` returns an `int` handle (`τ = Any`) ⇒ `isinstance` stays **symbolic**. Giving nodes a
  real `variant`/`record` `τ` is **[STDLIB]** work (the `class AST`/node-class stubs), gated on **[TOOL]
  Gap 6/7**.
- **Therefore Phase 3 `isinstance` needs both [TOOL] P4 (have) and [STDLIB] node classes (Phase 2).**
  You cannot dispatch on a type you have not given the value.
- **P5 link [SEAM]:** a node from `ast.parse("<constant>")` ([TOOL] §8.3) could carry a `τ` derived at
  verification time (root `Module`/`Expression` by mode), making `isinstance` on *that* node decidable
  before the full **[STDLIB]** Phase-2 model — **Modelled-relative-to-TCB**, gated on a driver (P5d).

## 8  P5 — the parser family  **[TOOL]** *(tool track)*

### 8.1  Two parsers, never conflated  **[TOOL]**

| | What it is | Owner |
|---|---|---|
| **Tool compile-time parser** | host `ast.parse` in `Module1_Ingestor` (~line 112) — parses the source under verification, **including any constant string passed to the family** | **[TOOL]** |
| **`pure_lib/astmod`** | the runtime *model* of `ast` for verified programs that inspect a parse result | **[STDLIB]** |

Executable members (`exec`/`eval`/`compile`) have **no** runtime data surface → they route through the
**[TOOL]** path only (constant → splice/evaluate; dynamic → havoc), never through `astmod`.
`ast.parse`/`literal_eval` have a data result and so *also* consume the **[STDLIB]** model for the
runtime case.

### 8.2  The one classifier: knowability of the source argument  **[TOOL]**

For every family call `g(s, …)`:

- **`s` compile-time constant** (literal, or a local provably bound to one — reuse P3 definite-
  assignment / constant-folding) → parse/evaluate at verification time (§8.3).
- **`s` dynamic** → conservative treatment (§8.4), **identically for every member**, so `exec(s)` and
  `ast.parse(s)` on the same dynamic `s` cannot diverge.

### 8.3  Constant source → faithful, with the right grade  **[TOOL]**

| Member | Constant-arg behaviour | Grade |
|---|---|---|
| `exec("…stmts…")` | **straight-line whitelist splice** (assignments + pure expressions ONLY); **reject** *all* control flow (`return`, `if`, `with`, `try`, `while`/`for` even with invariant, `break`/`continue`), `import`, nested `def`/`class`, nested `exec`. Invariant-bearing loops → **P5e**. | Modelled (splice = inline-equivalent, §8.5; parse step rel-TCB) |
| `literal_eval("…literal…")` | parse + evaluate → actual value, true `τ` (`-5:int`, `[1,2]:list`, …) | **Modelled (faithful)** |
| `eval("…closed pure expr…")` | fold a **closed** expr (literals + pure operators, **no free names, no calls**) | **Modelled (faithful)** |
| `eval("…name/call expr…")` | **not** free-decided → route through the splice path (`__tmp = expr`, whitelist: pure operators + **pure-function** calls only); else **dynamic** (§8.4) | conservative or splice |
| `compile/ast.parse("…", mode)` | parse → root `τ` `Module`/`Expression` by mode (with [STDLIB] Phase-2 node `τ`) | **Modelled-relative-to-TCB** |

Only `literal_eval` and closed `eval` are unqualifiedly faithful; parse-producing members are faithful
*relative to the TCB* (§9); the splice is sound *relative to the whitelist* (§8.5).

### 8.4  Dynamic source → conservative (Specified/`\trusted`)  **[TOOL]**

Mark the call site `\trusted reviewer: dynamic-exec`. Not a no-op:

1. **Scope havoc (decision C, wired on `main`).** Set `has_dynamic_exec = True` → `_scope_dyn_exec`
   **withholds the `\in_scope` decided-false direction** downstream. P5a only SETs the flag.
2. **Frame taint.** A worst-case mutator: surrounding `assigns`/HAPPY must treat it as able to write
   anything (the reference's rule for a non-exempt `\trusted`/`\abstract` mutator without `\preserves`).
3. **No decided result.** `eval`/`ast.parse`/`literal_eval` of a dynamic `s` → unconstrained value;
   the **[STDLIB]** Stubbed rows (§4.3/§4.4) are exactly this case.

### 8.5  Soundness — both halves, explicitly  **[TOOL]**

Easy half: **never decide a dynamic string** (§8.4). Hard half: the **constant `exec` splice** mutates
the unit of verification, and is sound **because of the whitelist**, not constancy —

- **No control-flow change:** the whitelist admits only straight-line assignments / pure-expression
  statements, so the splice cannot alter the CFG (`exec("return 5")` is *rejected*, not spliced).
- **Line-preservation + same dataflow:** introduced names enter the same P3 definite-assignment pass
  as hand-written assignments.
- **⇒ verification-equivalent to inline source** the tool already verifies soundly. The splice
  *relocates* code the verifier handles; it adds no new semantics. **Drop the whitelist and the
  equivalence fails.**
- **Parse-producing results are TCB-relative** (faithful only if the tool parser agrees with CPython);
  `literal_eval`/closed `eval` avoid this (trivial grammar / pure folding).

Same string ⇒ same verdict (§8.2): no member launders a fact another would refuse. Family analogue of
the `07-1839` three-valued fail-safe — a missing proof or a `\trusted`, never a wrong one.

### 8.6  Phasing — parser family  **[TOOL]** *(tool track)*

| Phase | Delivers | Acceptance | Owner |
|---|---|---|---|

| **P5b** constant straight-line `exec` splice | whitelist splice (§8.3) | **[PROVE]** spliced assignment visible after; **[typecheck]** any control flow / non-whitelisted code **rejected** (fail-loud) | [TOOL] |
