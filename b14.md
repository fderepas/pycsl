## Execution outcome (2026-06-30) — what was probed, what was fixed, what the plan got wrong

Executing this plan surfaced that its blocker model was **incomplete and partly inverted**. The keystone B1-a ("inline the sums") rests on an assumption that does not hold, and there is a **5th blocker** the plan never names, plus a **semantic ceiling** above B1–B4. The findings below are evidence-backed (standalone probes + a code-level audit), not inferred.

### What was LANDED (three byte-clean foundational compiler fixes + two corpus tests)

All three are **byte-identical across the full 624-file corpus `.mlw` sweep** (purely additive) and proven to work end-to-end via probes; no proof regressions (corpus emission unchanged ⇒ proofs unchanged):

1. **`str` record-field invariant witness** (`src/pycsl/module6_whyml/auto_trust.py`, `_build_witness_str`). A `str`-annotated record field is Why3 `string`, but the `by { … }` invariant-witness emitted the int `0` for it → Why3 type error. Now emits `""`. **This is the 5th blocker the plan never lists** — without it, *no* string-field record with a class invariant can be witnessed.
2. **`@dataclass` → record registration** (`src/pycsl/frontend/Module5_IREmitter.py`, `_collect_class_fields` + new `_is_dataclass_decorated`). A `@dataclass` has no `__init__`, so the field-collection walk found nothing and the class coarsened to the opaque `int` alias (`stmt.target` → abstract getattr). Now class-body AnnAssigns of a `@dataclass` are collected as record fields (same route as TypedDict/NamedTuple), `str`→`string`. **This is the real form of B1** — "inline the sums" alone is insufficient; the sums must *register as records*, which dataclasses did not until this fix. It also makes the real `src/pycsl/ir_schema.py` dataclasses first-class records (LINK 1).
3. **All-string f-string → faithful `string` concat** (`src/pycsl/module6_whyml/expressions.py`, `_handle_fstring_expr`) — **B2**. An f-string whose every segment is string-typed now lowers to a `str_concat_op`/`concat` chain (real Why3 `string`) instead of int-hash `str_concat`. Mixed f-strings keep the legacy int model → byte-identical.
4. Corpus regression tests **`0743`** (dataclass record param, body-faithful `str` field read) and **`0744`** (all-string f-string concat) — both verify SUCCESS and run PASS.

Combined, these make a body-faithful **`def f(stmt: AssignStmt) -> str: return stmt.target` with `ensures \result == stmt.target` formally prove** (probe), and an all-string f-string prove `ensures \result == "let " + name` (probe). The B1 + B2 + 5th-blocker plumbing is done and gated.

### Why the `_handle_*` conversions still do NOT close (the plan's two errors)

**Error 1 — the leaf/Wave split is real but the "leaf" methods aren't leaves.** A per-method state-mutation scan of the 12 `_handle_*` methods: **6 are clean** (`array_set`, `augassign`, `expr`, `fieldassign`, `fieldaugassign`, `ghost_array_set`) and **6 genuinely mutate transpiler state** (`assign`, `ghost_assign`, `critical_section`, `seq_assign`, `tuple_unpack`, `array_slice_set`) → the latter 6 need **B4** (transpiler-state record model). So the plan's "Wave 1 = 4–6 methods, Wave 2 needs B4" split is roughly correct.

**Error 2 (the fatal one) — the semantic ceiling sits ABOVE B1–B4.** Even the 6 "clean" methods are not tractable from B1+B2+B3-a. Every one calls `stmt.value.to_dict()` and then operates on the resulting `Dict` with rich Python — `dict.get(...)`, `str.endswith/rsplit/strip/replace`, `stable_hash` — while reading many `self.*` state fields and trusted siblings (`_expr_to_whyml`, `_add_abstract_op`, `_field_label`, `_field_type_for`). `\trusted` exists on these precisely because the bodies exceed PyCSL's current modeling (see `src/self-annotate/semantic-ceiling.md`). "Inline sums + f-string fix" does **not** make them prove; each needs real per-construct modeling (dict-over-record, `.to_dict()`, the string-builder ops). That is per-method modeling work, not a mechanical sweep.

## The 4 blockers

### B1 — Opaque `ir_schema` import (DOMINANT)
`src/self-annotate/src/module6_whyml/statements.py` does `from ir_schema import AssignStmt, stmt_from_dict, …`. In single-file verification, pycsl skips this ("external module, no local source found") → `AssignStmt` is opaque → `stmt.target` is an Any-typed getattr → the typed-schema payoff is lost.

### B2 — f-string hashing
The `_handle_*` bodies build the emitted WhyML string with f-strings: `f"{indent}let {safe_target} := {val}"`. pycsl lowers f-string LITERAL segments to hashed INTs (`stable_hash`) → `str_concat` receives an int where a string is expected → WhyML type error.

### B3 — Trusted sibling returns
`_handle_*` bodies call `self._expr_to_whyml(...)` and `self._stmts_to_whyml(...)` — themselves `\trusted` with `ensures True`. The emitted string DEPENDS on those return values, which are unmodeled, so a real `ensures \result == ...` can't pin the composed string.

### B4 — Self-mutation
Many `_handle_*` bodies mutate transpiler state: `self._dict_locals.add(...)`, `self._record_locals.add(...)`, `self._add_abstract_op(...)`, `self._array_locals.add(...)`. With no transpiler-state record model, the frame (`assigns`) can't be stated soundly.

## The plan

### B1 — Cross-file type resolution for self-annotate (the keystone)
**The problem:** pycsl's single-file mode skips `from ir_schema import AssignStmt`. The typed sum classes live in `src/pycsl/ir_schema.py` but the self-annotate copy at `src/self-annotate/src/module6_whyml/statements.py` can't see them.

**Three options (in preference order):**

#### Option B1-a (preferred): inline the typed sums into the self-annotate file
Instead of importing `AssignStmt` etc. from `ir_schema`, **inline the sum-class definitions** at the top of `src/self-annotate/src/module6_whyml/statements.py` (or a sibling `_ir_schema_sums.py` co-located in `src/self-annotate/src/module6_whyml/`). The self-annotate copy already inlines the real Module6 source; it can inline the IR-schema sums too. Then `stmt: AssignStmt` resolves to a concrete local class, and `stmt.target` is a typed field access.

This is the lowest-risk option: no pycsl cross-file machinery changes; the sums are already defined (Phase A); just copy them into the self-annotate tree. The downside is duplication (the sums exist in both `ir_schema.py` and the self-annotate copy) — but self-annotation already duplicates the compiler source, so this is consistent.

#### Option B1-b: teach pycsl to resolve local `src/` imports in self-annotate mode
Add a mode (or a `--include-path` flag) where `from ir_schema import X` resolves `src/pycsl/ir_schema.py` (the real source) and pulls in the sum-class definitions. This is the general fix but is a real pycsl feature (cross-file type resolution for the verifier's own consumption) and risks regressing the standing gate.

#### Option B1-c: stub `ir_schema` as a `#@ datatype`
Model `AssignStmt` etc. as a `#@ datatype stmt_ir = SAssign of string expr_ir | ...` in the self-annotate file (already partially done — `statements.py` has `#@ datatype stmt_ir = …`). But this is a logic-only type; the Python `stmt: AssignStmt` annotation still needs to resolve to it. This requires pycsl to treat a `#@ datatype` as a Python type annotation — non-trivial.

**Recommendation: B1-a** (inline the sums). It's the fastest, lowest-risk, and consistent with the self-annotate duplication model. If B1-a closes B1, B2–B4 become attackable.

### B2 — f-string literal-segment lowering
**The problem:** `f"{indent}let {x} := {val}"` — the literal segments `"let "` and `" := "` are lowered to `stable_hash("let ")` (an int), so `str_concat` gets `(int, string, int, string, ...)` → type error.

**The fix:** lower f-string literal segments as WhyML STRING literals, not int hashes. The f-string `f"let {x}"` is `ast.JoinedStr` with children `ast.Constant(str)` (literal) and `ast.FormattedValue` (interpolation). In `_py_expr_fstring` (`src/pycsl/frontend/Module5_IREmitter.py:1001`):
- literal segment (`ast.Constant` with str value) → lower to a `StrConcat`/`String` IR node (WhyML `string`), NOT a hashed int.
- interpolated segment → lower as the expression (which may be `str` or `int`).

Then the f-string becomes a `str_concat` chain of `string`-typed operands. For `int` interpolations (`{val}` where `val: int`), coerce via the existing `str_of_int`/`int_to_str` op (add if missing) OR keep the int-hash convention ONLY for non-string interpolations.

**Key invariant:** a f-string where ALL segments are string-typed (`f"{indent}let {name}"` with `indent: str`, `name: str`) must lower to a pure `string` expression. This is what B2 needs.

**Risk:** changing f-string lowering may regress the corpus (many drivers use f-strings). The standing gate (byte-diff) catches this. Mitigation: make the new lowering fire only when all segments are string-typed (the self-annotate case); int-segment f-strings keep the legacy hash behavior (byte-identical).

### B3 — Sibling-call contracts (`_expr_to_whyml`, `_stmts_to_whyml`)
**The problem:** `_handle_assign_stmt` calls `self._expr_to_whyml(stmt.value, ...)` and uses the return string. That sibling is `\trusted` with `ensures True`, so the return is unmodeled.

**The fix (two options):**

#### Option B3-a (preferred for the leaf cases): avoid the sibling call
For the LEAF `_handle_*` methods (the ones that emit a fixed string with no expression interpolation), there's no sibling call — B3 doesn't apply. These are the first to go body-faithful once B1+B2 clear. For the compositional ones that DO call `_expr_to_whyml`, the contract can be **weaker but real**: `ensures \result` (the result is a non-empty string) + `assigns \nothing` (no self-mutation) — without pinning the exact string. This is a real contract (not `\trusted`) that discharges from the sibling's `ensures True` (a string is returned).

#### Option B3-b: body-faithful the siblings too
Re-annotate `_expr_to_whyml` and `_stmts_to_whyml` body-faithful (they're in `expressions.py` / `statements.py`, same self-annotate tree). This is recursive (the siblings have their own blockers) — but the leaf expression emitters (`_handle_str`, `_handle_number`, `_handle_var`) are simpler and may go body-faithful first, giving the compositional siblings real postconditions to compose.

**Recommendation: B3-a** for the first wave (weak-but-real contracts on the compositional methods), B3-b as a follow-up (body-faithful the siblings once their leaf cases clear).

### B4 — Transpiler-state record model
**The problem:** `self._dict_locals.add(...)`, `self._add_abstract_op(...)` mutate the emitter object. No model for `self`'s state → `assigns` can't be stated.

**The fix:** model the emitter (`self`) as a WhyML record with the mutable fields (`_dict_locals: set string`, `_record_locals: set string`, `_array_locals: set string`, `_abstract_ops: list string`, …). The `self._dict_locals.add(x)` becomes a field update `self._dict_locals = add(self._dict_locals, x)`. The `assigns` clause lists the mutated fields.

This is the heaviest blocker — it requires:
1. A `#@ class invariant` / record declaration for the emitter class (`StatementEmissionMixin`).
2. Field-update lowering for `self.field.add(...)` / `self.field = ...`.
3. The `assigns` clause enumerating the mutated fields per method.

**Recommendation:** defer B4. The methods that DON'T mutate `self` (the leaf emitters: `_handle_pass_stmt`, `_handle_break_stmt`, `_handle_continue_stmt`, `_handle_return_stmt`, and the fixed-string cases of `_handle_assign_stmt`) can go body-faithful with `assigns \nothing` once B1+B2 clear. B4 only blocks the methods that genuinely mutate state (the compositional ones that call `self._add_abstract_op`). Those stay `\trusted` until the transpiler-state record model lands.
