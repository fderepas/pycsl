# 07-1321-req — PyCSL Tool Fix: bytes/bytearray and array-ref lowering

**Date:** 2026-06-07
**Context:** The `pure_lib/os/UnixInodeFileSystem.py` filesystem model (1100+ lines,
30+ syscalls) fails to type-check in Why3 due to two code-generation bugs in the
WhyML emitter. These are pre-existing issues unrelated to the R1+R2 HAPPY merge
(verified by bisecting back to `cd00e92`). The file was previously reported as "98%
proven" but that result is not reproducible with the current tool + Why3 1.8.2 setup.

---

## Bug 1 — `bytes()`/`bytearray()` constructor stubs typed as `int → int`

### Symptom

```
File "…/UnixInodeFileSystem.mlw", line 88, characters 13-110:
This expression has type array.Array.array int @rho,
but is expected to have type int
```

### Root cause

When the Python source calls `bytes([...])` or `bytearray()`, the WhyML emitter
reaches the "unannotated callee" fallback (expressions.py line 954–972) which generates:

```whyml
val bytes_1 (x0: int) : int
val bytearray_0 () : int
```

Both parameter and return types should be `array int`, not `int`. The `bytes()`
constructor is not handled in `_call_named_builtins` (unlike `list()`, `sorted()`,
`dict()`, etc.).

### Affected code

```python
def _pack_uint16_be(v: int) -> list:
    return bytes([(v >> 8) & 0xFF, v & 0xFF])  # bytes_1 called with array int arg

def _pack_inode(fields: list) -> list:
    parts = bytearray()       # bytearray_0 returns int, not array int
    parts += _pack_uint32_be(fields[0])  # int += array int → type mismatch
    ...
    return bytes(parts)       # bytes_1 called with array int arg
```

### Fix

Add `bytes` and `bytearray` to `_call_named_builtins` (parallel to the existing
`list` handler at line 1169):

```python
if func_name == "bytes" and len(args) <= 1:
    if args:
        self._add_abstract_op("val bytes_new (x: array int) : array int")
        return f"(bytes_new {self._array_coerce_arg(args[0])})"
    self._add_abstract_op("val bytes_empty () : array int\n  ensures { Array.length result = 0 }")
    return "(bytes_empty ())"

if func_name == "bytearray" and len(args) <= 1:
    if args:
        self._add_abstract_op("val bytearray_new (x: array int) : array int")
        return f"(bytearray_new {self._array_coerce_arg(args[0])})"
    self._add_abstract_op("val bytearray_empty () : array int\n  ensures { Array.length result = 0 }")
    return "(bytearray_empty ())"
```

### Acceptance criteria

- [ ] `bytes([1, 2, 3])` generates `val bytes_new (x: array int) : array int`
- [ ] `bytearray()` generates `val bytearray_empty () : array int` with length 0 ensures
- [ ] `_pack_uint16_be` and `_pack_inode` compile to well-typed WhyML
- [ ] No regression on the 570/570 pycsl-reference corpus

## Bug 2 — Array-ref locals not dereferenced at call sites

### Symptom

```
File "…/UnixInodeFileSystem.mlw", line 526, characters 50-55:
This expression has type ref (array.Array.array int @rho1) @rho,
but is expected to have type array.Array.array int @rho2
```

### Root cause

When a local variable is assigned a list literal AND later mutated (element
assignment), the emitter wraps it in a `ref`:

```whyml
let inode = ref (let _alit = Array.make 18 0 in _alit[1] <- 1; ...; _alit) in
```

But when this variable is passed as an argument to a function call, the emitter
passes `inode` (the ref cell) instead of `!inode` (the dereferenced array):

```whyml
let _ = (self__write_inode_2 !inode_num inode) in  (* BUG: should be !inode *)
```

### Affected pattern

```python
inode = [0, 1, 1, mode, 0, 0, 0, 0, p_block, 0, 0, 0, 0, 0, 0, 0, 0, 0]
inode[7] = self._now()  # this causes inode to be wrapped in ref
self._write_inode(inode_num, inode)  # BUG: inode should be dereferenced
```

The pattern occurs in: `sys_creat`, `sys_mkdir`, `sys_symlink`, and any method that
creates a list literal, mutates an element, then passes it to a callee.

### Fix

In the call-site argument coercion logic (likely in `_coerce_dotted_args` or the
generic call emission), check whether the argument variable is in the set of
ref-wrapped locals. If so, emit `!var` instead of `var`.

The emitter already tracks which locals are ref-wrapped (used for `!var` in
element-assignment and while-loop contexts). The fix is to apply the same deref
at call sites.

### Acceptance criteria

- [ ] `self._write_inode(inode_num, inode)` emits `(self__write_inode_2 !inode_num !inode)`
- [ ] The pattern "create list, mutate element, pass to callee" type-checks
- [ ] `UnixInodeFileSystem.py` compiles to well-typed WhyML (all 1100+ lines)
- [ ] No regression on the 570/570 pycsl-reference corpus

## Bug 3 — `b'\x00' * N` byte-literal repetition in slice assignments

### Symptom

Not a type error but generates an `int` where `array int` is needed in contexts like:

```python
self.disk[offset:offset + 512] = b'\x00' * 512
```

### Root cause

The byte literal `b'\x00'` is lowered to an integer (its hash/length), and
`b'\x00' * 512` becomes integer multiplication. The slice assignment then tries to
assign an `int` to an `array int` slice.

### Workaround (applied)

Replace `b'\x00' * N` with `[0] * N` in the source. However, this should be
handled by the tool since `b'...'` literals are supposed to lower to `array int`
per the `missing-bytes-struct-feature.md Phase 1` design.

### Fix

Ensure that `b'...'` literals (and `b'...' * N` repetitions) lower to `array int`
values rather than integer hashes in all contexts, particularly slice assignment RHS.

### Acceptance criteria

- [ ] `b'\x00' * 32` generates an `Array.make 32 0` (or equivalent `array int`)
- [ ] `self.disk[a:b] = b'\x00' * N` type-checks
- [ ] No regression on the 570/570 pycsl-reference corpus
