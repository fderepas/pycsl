# Three verifier gaps surfaced by the faithful `pure_lib/strmod/` proof

**Context.** Rebuilding `pure_lib/strmod/` off int-coercion onto real `str` (commit `a50bc61`,
applying `docs/formal-filesystem.md`) exposed three faithfulness gaps in the verifier. All three are
about **non-`int` types flowing through control-flow / call boundaries** — exactly the surface the
no-more-int doctrine targets. Each was *worked around* in the strmod model (so the proof is clean and
byte-gated); none is *fixed* in the tool. This file describes each precisely as a follow-up spec.

Common thread: gaps **#2 and #3** both stem from the same missing piece — the **callee/parameter
faithful-type is not threaded** to the call/`len` lowering. Gap **#1** is independent: the early-return
exception is hardcoded to `int`.

Recommended fix order: **#1 first** (broadest — blocks every faithful non-`int`-returning function),
then **#3** and **#2** together (shared type-threading).

---

## Gap 1 — `exception Return` is hardcoded `int`: a non-`int`-returning function with an *early* return won't type-check

**Severity: HIGH / broad.** Blocks ANY function returning a faithful non-`int` *scalar* (`str`, `real`,
record, variant) that has an early `return` (a `return` before the tail, e.g. inside an `if` or a loop).

**Symptom.** Type-check fails: `This expression has type string, but is expected to have type int`
(or `real`, etc.) at the early-return raise / the body's catch.

**Reproducer.**
```python
#@ ensures \str_length(\result) >= 0
def f(s: str) -> str:
    if s == "":
        return s          # early return -> raise (Return s)
    return g(s)           # tail return
```

**Root cause.**
- `src/pycsl/module6_whyml/preamble.py:427` unconditionally declares the generic early-return exception
  as `exception Return int` — its payload type is `int`.
- The catch is chosen in `_wrap_body_with_return_catch` (`src/pycsl/module6_whyml/statements.py:911`):
  - `return_type == "unit"` → `with Return_void -> ()` (preamble.py:436)
  - tuple (`arity > 0`) → `with Return_{arity} r -> r` (preamble.py:443)
  - `return_type == "array int"` → `with Return_seq s -> materialize s` (preamble.py:433)
  - **else → `with Return r -> r`** — the `int` arm.
- For `return_type == "string"` (and any other non-`int` scalar) execution falls to the **else** arm, so
  the early `raise (Return s)` carries a `string` while `exception Return int` expects `int` → ill-typed.
- There is **no `Return_str`** (nor a general `Return_<T>`). The existing `Return_seq`/`Return_void`/
  `Return_{arity}` machinery is exactly the pattern that was never extended to scalar non-`int` returns.

**Workaround used in strmod.** Avoided early returns entirely: `format_field` is written as a single
tail conditional expression — `return v if spec == "" else _format_field_nonempty(spec, v)` — so no
`raise (Return ...)` is ever emitted. Faithful Python, but it forces an unnatural single-tail style and
does not scale to functions that genuinely need early exits.

**Fix.** Generalize the early-return exception to the function's WhyML return type:
1. `preamble.py`: add `exception Return_str string` gated on a `needs_return_str` flag (mirror the
   existing `needs_return_seq` plumbing at preamble.py:433 / 256). Ideally generalize to `Return_<T>`
   keyed on the lowered return type (`string`, `real`, a record type, …).
2. `statements.py:911` `_wrap_body_with_return_catch`: add a `return_type == "string"` branch →
   `with Return_str r -> r` (and the general `Return_<T>` arm).
3. `_handle_return_stmt` (the raise site): raise `Return_str` (resp. `Return_<T>`) when the function's
   return type is `string` (resp. that type), instead of the generic `Return`.

This is the single highest-value fix: it unblocks faithful early-returning code for *every* non-`int`
return type, which any real string/float/record library needs.

## Gap 2 — `len(e)` on a call returning `str` lowers to the opaque sequence `iter_length`, not `str_length_op`

**Severity: MEDIUM.** Mistypes `len()` of any string-returning *call* (notably an imported stub).

**Symptom.** `len(capwords(s))` lowers to the opaque `iter_length` (a `seq`-style length over an
int-hashed argument) instead of `str_length_op` (`String.length`), producing wrong/ill-typed WhyML.

**Reproducer.**
```python
return len(capwords(s, sep))         # WRONG: routes to iter_length
# vs the workaround:
r: str = capwords(s, sep)
return len(r)                        # OK: r is a str-typed Var -> str_length_op
```

**Root cause.**
- `_handle_len_call` (`src/pycsl/module6_whyml/expressions.py:573`) routes to `str_length_op` only when
  `self._is_string_expr(arg_ir)` holds (~expressions.py:616); otherwise it falls through to the opaque
  iter-length path (`stmt_control_flow.py:136`/`165`, `iter_length`).
- `_is_string_expr` (`src/pycsl/module6_whyml/expressions.py:334`) recognizes: `String`/`StrConcat`/
  `StrSub` nodes, a `Var` whose `_current_symbol_table` type is `"str"`, `Subscript`/`SliceAccess` of a
  string, and `BinOp(+)` of two strings. It has **no case for a `Call`/`CallExpr` node** — it never
  consults the *callee's declared return type*. So a `len(<call returning str>)` is not detected as
  string-typed.

**Workaround used in strmod.** Bind the call result to a `str`-typed local first
(`r: str = capwords(s, sep)`); then the `len` argument is a `str`-typed `Var`, which `_is_string_expr`
recognizes via `_current_symbol_table`.

**Fix.** Extend `_is_string_expr` (expressions.py:334) with a `Call`/`CallExpr` case that returns `True`
when the callee's declared return type is `str`. This requires threading the callee return-type table
(the module-method / imported-function return types — the same table gap #3 needs) into the expression
emitter so `_is_string_expr` can look up `func_name -> return_type`.

## Gap 3 — an omitted trailing default arg is filled with int `0`, regardless of the parameter's declared type

**Severity: MEDIUM.** Mistypes any faithful non-`int` parameter that has a default and is omitted at a
call site.

**Symptom.** Calling `capwords(s)` (omitting `sep: str = None`) lowers to `capwords s 0` — an int `0`
applied to the `string` parameter `sep` → type mismatch.

**Reproducer.**
```python
#@ \trusted reviewer: python-stdlib
def capwords(s: str, sep: str = None) -> str: ...
...
capwords(s)        # sep omitted -> filled `0` (int) into a `string` param
```

**Root cause.**
- The callee's positional defaults are collected in Module 5 as `param_defaults` (param name → default
  IR), `src/pycsl/frontend/Module5_IREmitter.py:1777-1784`.
- At the call site, when fewer args than the callee arity are passed, the missing trailing params are
  filled by **lowering the default expression**: `src/pycsl/module6_whyml/expressions.py:1088-1094`
  (`args = args + [self._expr_to_whyml(defaults[nm], ...)]`).
- The default `None` (for `sep: str = None`) lowers to `0` — PyCSL's int model of `None` — which is
  **not coerced to the parameter's declared faithful type** (`string`). So a `string` parameter is
  filled with an `int`.

**Workaround used in strmod.** Pass `sep` explicitly (a real string) at the call site, bypassing the
default-fill. (This also strengthened the formal driver — the capwords bound now holds for all separators.)

**Fix.** Lower the filled default **at the parameter's declared faithful type**: an absent/`None` default
for a `str` param should fill `""` (or a faithful sentinel), for a `real` param `0.0`, etc. — never a
bare int `0`. The type-aware pattern already exists in the codebase at
`src/pycsl/module6_whyml/expr_ghost_spec_ops.py:74` (`default = '""' if ptype == "str" else "0"`); apply
the same dispatch in the call-arg fill (expressions.py:1088), consulting the parameter's WhyML type.

## Summary

| # | Gap | Root cause (file:line) | Fix | Severity |
|---|-----|------------------------|-----|----------|
| 1 | early `return` in a non-`int`-returning fn fails to type-check | `exception Return int` hardcoded — preamble.py:427; no `Return_str` arm in `_wrap_body_with_return_catch` statements.py:911 | add `Return_str`/`Return_<T>` (mirror `Return_seq`) | **HIGH/broad** |
| 2 | `len(<call returning str>)` → opaque `iter_length` | `_is_string_expr` has no `Call` case — expressions.py:334; callee return type not consulted | add a `Call` case keyed on the callee's `str` return type | MEDIUM |
| 3 | omitted defaulted non-`int` param filled with int `0` | default lowered without coercing to the param's type — call-fill expressions.py:1088, defaults from Module5:1777 | lower the default at the param's faithful type (pattern: expr_ghost_spec_ops.py:74) | MEDIUM |

Gaps #2 and #3 share the missing **callee/parameter faithful-type threading** into the expression
emitter; fixing one makes the other cheap. Gap #1 is independent and should go first — it is the
broadest blocker for faithful non-`int`-returning code (`str`, `real`, record, variant) and is a direct
extension of the already-present `Return_seq` / `Return_void` / `Return_{arity}` machinery.
