# Global Audit Guide: From Rocq Theorem to PyCSL Annotation

> How to fully audit the chain from a formal statement such as
> `SAssign x e => Qn (update st x (eval_expr st e))` to the `#@` annotation
> on the Python implementation.
>
> Related: `README.md` (Layer 3 concept), `../README.md` (trust chain overview),
> `pycsl-wp-spec.mlw` (the Why3 spec module).

---

## 1. The Five-Link Chain

Every WP arm traces through five links. Two links are machine-checked;
one is human-audited; two are generated.

```
[1] Rocq fixpoint arm
    src/formal-semantics/rocq/Phase4_WP.v
        │
        │  human-audited: ensures clause written by inspection of the Rocq arm
        ▼
[2] Why3 val spec
    src/self-annotate/self-annotate-layer3/pycsl-wp-spec.mlw
        │
        │  machine-checked: Why3 clone/refinement verifies the binding below
        ▼
[3] WhyML let implementation
    generated .mlw (e.g. test-suite/corpus/pycsl-reference/0006.mlw)
        │
        │  generated by Module6_WhyMLTranspiler.py from Python source
        ▼
[4] Python handler
    src/pycsl/Module6_WhyMLTranspiler.py
        │
        │  machine-checked: pycsl --no-proof verifies #@ annotations via Why3
        ▼
[5] PyCSL #@ annotation
    src/self-annotate/rocq/Module6_WhyMLTranspiler.py  (annotated copy)
```

**Machine-checked links**: [2]→[3] (Why3 clone proof) and [4]→[5] (pycsl --no-proof).

**Human-audited link**: [1]→[2] — the `ensures` clause of the Why3 `val`
mirrors the Rocq arm by inspection. The audit checklist in Section 4 makes
this step structured and repeatable.

**Generated links**: [3] is produced by the PyCSL transpiler; [5] is written
by a human annotator following the spec.

## 2. Full Worked Example: `SAssign`

### Link 1 — Rocq (`Phase4_WP.v:23–24`)

```coq
| SAssign x e =>
    Qn (update st x (eval_expr st e))
```

Reading: after executing `SAssign x e`, the normal-completion postcondition `Qn`
holds in the state where `x` has been updated to `eval_expr st e`. The state
transformation is exactly `update st x (eval_expr st e)`.

### Link 2 — Why3 val spec (`pycsl-wp-spec.mlw`, `handle_assign`)

```whyml
(* Phase4_WP.v:23–24
 *   | SAssign x e =>
 *       Qn (update st x (eval_expr st e)) *)
val handle_assign (x: ident) (e_val: value) (st: state) : state
  ensures { result = update st x e_val }
```

**Audit note — how `ensures` mirrors the Rocq arm:**

| Rocq | Why3 | Correspondence |
|---|---|---|
| `Qn (update st x (eval_expr st e))` | `result = update st x e_val` | `Qn` is the identity postcondition; `e_val` stands for `eval_expr st e` |
| `update st x v` | `update st x v` | identical (same definition, different representation) |

The only difference: in Rocq, `e_val` is computed by `eval_expr st e` in the
Rocq fixpoint. In the Why3 spec, the caller passes `e_val` as a pre-evaluated
argument (the expression evaluator is abstract in the spec). This is a
deliberate simplification — the spec does not embed the expression evaluator.

### Link 3 — Generated WhyML (example: `x = 5`)

Source Python:
```python
x = 5
```

Generated WhyML (`_handle_assign_stmt`, first occurrence of `x`):
```whyml
let x = ref 5 in
()
```

Why3 verification obligation (from the user's `#@ ensures`):
```
ensures { !x = 5 }
```

This matches `lookup (update st "x" (VInt 5)) "x" = VInt 5`, which is exactly
what `handle_assign "x" (VInt 5) st` promises in the spec.

To run Why3 on a generated file:
```bash
why3 prove test-suite/corpus/pycsl-reference/0001.py.mlw -P Alt-Ergo
```

### Link 4 — Python handler (`Module6_WhyMLTranspiler.py:1372–1444`)

Function: `_handle_assign_stmt(self, stmt, rest, local_refs, declared_refs, indent, in_loop)`

Key logic:
- `target = stmt["target"]` — the variable name (`x`)
- `val = self._expr_to_whyml(stmt["value"], local_refs)` — evaluates the RHS
- First occurrence: emits `let {target} = ref {val} in`
- Reassignment: emits `{target} := {val}`

The function calls `_expr_to_whyml` (the `eval_expr` analogue) and then
emits a WhyML assignment. This is the structural realisation of
`update st x (eval_expr st e)`.

### Link 5 — PyCSL annotation (annotated copy)

```python
def _handle_assign_stmt(self, stmt: Dict[str, Any], rest: List[Dict[str, Any]],
                         local_refs: Set[str], declared_refs: Set[str],
                         indent: str, in_loop: bool) -> str:
    #@ assigns self._known_collection_sizes, self._known_collection_elements
    #@ assigns self._array_locals, self._dict_locals, self._lambda_locals
    #@ assigns self._record_locals, self._abstract_ops
    #@ ensures \result != ""
```

**Note on the strength gap**: The `#@` annotation is structurally weaker than
the Why3 spec. It asserts non-empty output (`\result != ""`), not that the
output implements `update st x e_val`. This is the Layer 1/Layer 3 split:
- Layer 1 verifies structural properties (frame conditions, non-empty output).
- Layer 3 verifies semantic equivalence (output implements the WP arm).

Both are necessary. Neither is sufficient alone.

## 4. Audit Checklist

For each WP arm, work through these checks in order. Each check has a
`[machine]` or `[human]` tag indicating who verifies it.

### Check A — Rocq source is current `[human]`

1. Open `src/formal-semantics/rocq/Phase4_WP.v`.
2. Find the arm cited in the `pycsl-wp-spec.mlw` comment (e.g., `:23–24`).
3. Confirm the Rocq text matches the comment verbatim.
4. If the line numbers have shifted (e.g., due to a Rocq edit), update the
   comment in `pycsl-wp-spec.mlw`.

### Check B — Why3 ensures mirrors Rocq arm `[human]`

For the `ensures` clause of each `val`:

1. Write out the Rocq arm's state transformation as a mathematical equation
   (e.g., `result_state = update st x (eval_expr st e)`).
2. Confirm the `ensures` clause expresses the same equation, substituting:
   - `Qn = λst'. st' = result` (identity postcondition)
   - Pre-evaluated arguments (e.g., `e_val = eval_expr st e`)
3. If the ensures clause differs structurally, it must be justified in a
   comment explaining the simplification.

Acceptable simplifications:
- Moving from `eval_expr st e` to a pre-evaluated `e_val` argument.
- Using `M.map` instead of Rocq's association list for the state type.

Non-acceptable simplifications:
- Dropping a conjunct of the SWhile WP rule.
- Weakening the SArraySet bounds check.

### Check C — Python handler line numbers are current `[human]`

Run:
```bash
grep -n "def _handle_\|def _stmts_to_whyml\|def transpile" \
  src/pycsl/Module6_WhyMLTranspiler.py
```

Compare against the table in Section 3. Update the table if line numbers
have shifted.

### Check D — Why3 spec parses and type-checks `[machine]`

```bash
why3 prove src/self-annotate/self-annotate-layer3/pycsl-wp-spec.mlw \
     -P Alt-Ergo 2>&1 | grep -E "Valid|Unknown|Timeout|Error"
```

Expected: all goals `Valid` or `Unknown` (no `Error`). An `Unknown` on an
axiom's consistency check is acceptable — axioms are not goals. A type error
is a blocker.

### Check E — Layer 1 annotation is present and parseable `[machine]`

```bash
source .venv/bin/activate
python3 src/pycsl/pycsl.py --no-proof \
  src/self-annotate/rocq/Module6_WhyMLTranspiler.py
```

Expected: exit 0. Any parse error in a `#@` annotation is a blocker.

### Check F — A test case exercises this arm `[machine]`

Each WP arm should be covered by at least one test in
`test-suite/corpus/pycsl-reference/`. The test's generated `.mlw` file
should contain the expected WhyML keyword for the arm:

| Arm | Expected WhyML pattern |
|---|---|
| SSkip | `()` |
| SAssign | `:=` or `let … = ref` |
| SAugAssign | `:= … +` / `-` / `*` |
| SArraySet | `<-` (array write) |
| SSeq | `;\n` (statement separator) |
| SIf | `if … then … else` |
| SWhile | `while … do … done` with `invariant { … }` and `variant { … }` |
| SFor | `while … do … done` with `_pycsl_idx` |
| SReturn | `raise Return` or bare value return |
| SContinue | `raise PyCSL_Continue` |

Run:
```bash
python3 src/pycsl/pycsl.py --no-proof test-suite/corpus/pycsl-reference/<N>.py
grep -l "pattern" test-suite/corpus/pycsl-reference/*.mlw
```

## 5. The SWhile Three-Conjunct Check

The SWhile WP rule (Phase4_WP.v:45–66) has three conjuncts. The audit
must check all three independently because each maps to a different obligation
in the implementation.

```coq
| SWhile inv var cond body =>
    eval_contract st pre_st None inv               (* [C1] inv at entry *)
    /\ (forall st',                                (* [C2] body step *)
         eval_contract st' pre_st None inv ->
         eval_bool st' cond = true ->
         wp body (fun st'' =>
           eval_contract st'' pre_st None inv /\
           eval_variant st'' pre_st var < eval_variant st' pre_st var /\
           eval_variant st'' pre_st var >= 0) ...)
    /\ (forall st',                                (* [C3] exit post *)
         eval_contract st' pre_st None inv ->
         eval_bool st' cond = false ->
         Qn st')
```

**C1** (`check_while_inv_entry`): The `#@ loop invariant` annotation in the
generated WhyML ensures this. Why3 checks the invariant holds at loop entry.

**C2** (`check_while_body_step`): The `#@ loop invariant` + `#@ loop variant`
annotations together ensure this. Why3 checks that the body preserves the
invariant and decreases the variant on every iteration.

**C3** (`handle_while_exit`): This is the exit postcondition. In Why3, the
`while` statement's `ensures` (derived from the user's `#@ ensures`) is
checked after the loop exits. The state threading (`result = st`) confirms
no state is dropped.

In `_handle_while_stmt` (Module6, line 1446), look for:
- The loop condition emission → C1/C3 boundary
- The invariant and variant emission (`invariant { … }` / `variant { … }`) → C2
- The body emission → C2 body step
