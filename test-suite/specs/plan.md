# SYSTEM DIRECTIVE
Your objective is to validate that the formal mathematical models generated by PyCSL (`Module5_IREmitter` and `Module6_WhyMLTranspiler`) perfectly match the runtime semantics of the CPython reference implementation. 

You will execute the following 3-phase compliance architecture to create a **Dual-Oracle Test Suite**.

---

## PHASE 1: Implement the Dynamic Oracle (Runtime Assertion Generator)

**Objective:** Transform static PyCSL Hoare-logic comments into executable runtime checks to establish the dynamic ground truth.

**Agent Actions:**
1. Read the target Python test file (`.py`).
2. Parse the AST and extract all PyCSL contract comments (`#@ requires`, `#@ ensures`, `#@ loop invariant`).
3. Inject standard Python `assert` statements into the execution flow:
   * **Preconditions (`#@ requires <expr>`):** Inject `assert <expr>, "Precondition failed"` at the very beginning of the function body.
   * **Postconditions (`#@ ensures \result == <expr>`):** Capture the return value in a temporary variable (e.g., `_result`), inject `assert _result == <expr>, "Postcondition failed"`, and return `_result`.
4. Output a temporary executable file (e.g., `test_target_instrumented.py`).

**Expected Output:** An executable script where formal contracts are strictly enforced by the CPython interpreter at runtime.

---

## PHASE 2: Generate the Semantic Test Corpus

**Objective:** Build a targeted suite of test scripts that stress-test the boundary conditions where SMT solver default mathematics frequently diverge from CPython's execution model.

**Agent Actions:**
Generate isolated Python scripts. Each script MUST contain a heavily annotated function and a `__main__` block that calls the function with specific edge-case arguments.

**Focus Areas for Corpus Generation:**
* **Modulo and Floor Division on Negatives:** * *Test:* `-5 % 3` and `-5 // 3`. 
  * *Context:* CPython modulo inherits the sign of the divisor. Many SMT solvers use Euclidean division. PyCSL must bridge this gap.
* **Integer Boundaries:** * *Test:* Exceeding standard 32-bit and 64-bit integer limits.
  * *Context:* CPython handles arbitrarily large integers. Verify Why3/Alt-Ergo does not silently overflow.
* **Boolean Coercion (Truthiness):**
  * *Test:* `if 1:`, `if 0:`, `if -1:`.
  * *Context:* Ensure IR translation accurately reflects CPython's implicit boolean casting.
* **Short-Circuit Evaluation:**
  * *Test:* `True or undefined_function()`.
  * *Context:* Ensure the formal proof does not attempt to evaluate the right-hand side if the left-hand side is sufficient.

---

## PHASE 3: Dual-Execution Validation & Truth Table Evaluation

**Objective:** Execute the test corpus through both the Static Oracle (PyCSL) and the Dynamic Oracle (CPython), compare the results, and strictly categorize the engine's compliance.

**Agent Actions:**
For every file in the Semantic Test Corpus, execute the following two paths concurrently:

* **PATH A (Static Oracle):** * Command: `./pycsl <test_file.py>`
    * Capture: SMT Solver Output (`Valid`, `Invalid`, or `Unknown`).
* **PATH B (Dynamic Oracle):**
    * Command: `python3 <test_file_instrumented.py>`
    * Capture: Exit Code (`0` for Pass, `1` for AssertionError).

**Evaluation Matrix (The Truth Table):**
Evaluate the paired outputs using the following strict logic. Any deviation from `SUCCESS` requires logging an incident report with the exact AST node and WhyML translation.

| Path A (PyCSL / SMT) | Path B (CPython Runtime) | Classification | Agent Directive |
| :--- | :--- | :--- | :--- |
| **Valid** | **Pass (Exit 0)** | ✅ **SUCCESS** | Proceed to next test. PyCSL perfectly models safe code. |
| **Invalid / Unknown** | **AssertionError (Exit 1)** | ✅ **SUCCESS** | Proceed to next test. PyCSL perfectly caught a real runtime bug. |
| **Invalid / Unknown** | **Pass (Exit 0)** | ⚠️ **FALSE POSITIVE** | **Flag for Review.** PyCSL's translation is too strict, or the solver timed out. The mathematical model needs refinement, but it is safe. |
| **Valid** | **AssertionError (Exit 1)** | 🚨 **CRITICAL SOUNDNESS BUG** | **HALT PIPELINE.** PyCSL proved the code was safe, but CPython crashed. The formal model in `Module6_WhyMLTranspiler` is mathematically incorrect and deeply untrustworthy. |

**Final Output:** A compliance report detailing all tested nodes, categorized by the Truth Table, with immediate alerts generated for any **CRITICAL SOUNDNESS BUG**.

# REVIEW — Issues and Recommendations

## Issue 1: Contract Language ≠ Python (Phase 1 is underspecified)

Phase 1 proposes injecting `assert <expr>` directly from `#@` comments. But
PyCSL contracts are **not Python expressions**. They contain constructs that
have no direct Python equivalent:

| Contract construct | Problem for runtime injection |
|---|---|
| `\result` | Not a Python identifier; requires rewriting `return` statements to capture the value |
| `\old(expr)` | Requires snapshotting state at function entry, then comparing at exit |
| `\forall i; body` / `\exists i; body` | Quantifiers — unbounded domain, no Python equivalent. Must bound the range and use `all()`/`any()` |
| `==>` (implies), `<==>` (iff) | Not Python operators; need translation to `not a or b` / `a == b` |
| `#@ assigns \nothing` / `#@ assigns x` | Frame conditions; requires snapshotting all mutable state and comparing after call |
| `#@ loop invariant` | Must be checked at loop entry, end of each iteration, and loop exit — not just a single assert |
| `#@ loop variant` | Must verify strictly decreasing and non-negative — requires capturing previous value each iteration |
| `#@ class invariant` | Must be checked at entry and exit of every method |

**Consequence:** Phase 1 is not an "inject assert" task — it is building a
mini-compiler from the PyCSL contract DSL to executable Python runtime
checks. This is a substantial module that needs its own design.

## Issue 2: Testing unsupported operators (Phase 2)

The README explicitly states:

> **Not supported in contracts:** `//`, `%`, `len(...)`, function calls,
> string literals, `True`/`False`/`None`.

Phase 2 proposes testing `%` and `//` in contracts. These operators can
appear in **Python code bodies** but NOT in `#@` annotations. The test
corpus must distinguish between operators in contracts vs. operators in
code. The semantic gap being tested is in how Module6 translates the
**Python body** (which may contain `%`, `//`) to WhyML, not the contracts.

## Issue 3: Missing feature coverage (Phase 2)

The plan focuses on 4 niche edge cases but ignores the core features PyCSL
actually implements. Based on the codebase (`tests/to_annotate/`, modules,
README), missing categories include:

| Feature | Reference files | Priority |
|---|---|---|
| Class mutable records (Level 2) | `026-` to `030-` | High |
| Class invariants (Level 3) | `031-` to `040-` | High |
| Quantifiers (`\forall`, `\exists`) | `086-` to `091-` | High |
| Array contracts (`valid`, `separated`) | `056-` to `060-` | High |
| `\old` expressions | `027-`, `066-` to `070-` | Medium |
| Memory models (hoare/typed/store) | `061-` to `075-` | Medium |
| 2D matrices | `081-` to `085-` | Medium |
| `for` loops | `047-` to `055-` | Medium |
| Label-at (`@`) expressions | `076-` to `080-` | Medium |
| min/max builtins | `046-` | Low |
| Frame conditions (`#@ assigns`) | all annotated files | Medium |

## Issue 4: No pipeline unit/integration tests

The plan only covers end-to-end testing (pycsl ↔ CPython). There is no
strategy for testing individual modules:

- **Module 1 (Ingestor):** Does it correctly extract all `#@` comments?
- **Module 2 (Parser):** Does it correctly parse contract expressions?
- **Module 3 (Weaver):** Does it attach contracts to the right AST nodes?
- **Module 4 (SemanticAnalyzer):** Does it catch undeclared variables?
- **Module 5 (IREmitter):** Does it produce correct JSON IR?
- **Module 6 (WhyMLTranspiler):** Does it generate valid WhyML?

A bug in Module 1 that silently drops a contract would never be caught by
the dual-oracle approach — both oracles would agree (vacuously).

## Issue 5: Oversimplified SMT output model (Phase 3)

`pycsl` uses Why3's `split_vc` strategy, which decomposes each function
into multiple sub-goals. A single function can produce:
- Goal 1: Valid
- Goal 2: Valid
- Goal 3: Unknown (timeout)

The truth table treats the output as a single {Valid, Invalid, Unknown},
which is insufficient. The evaluation logic needs to handle **per-goal**
results and aggregate them.

## Issue 6: No negative test cases

The plan has no coverage for:
- **Malformed contracts** (testing parser error paths)
- **Semantic errors** (undeclared variables, type mismatches)
- **Files with no contracts** (should pass trivially)
- **Unsupported Python features** (should produce clear errors)
- **Intentionally buggy code with correct contracts** (should fail proof)

These are essential for testing the robustness of the pipeline.

# REVISED PLAN

Based on review, the following revised architecture is adopted.

**Scope decisions:**
- Goal: End-to-end dual-oracle soundness testing.
- Phase 1 requires a full **contract-to-Python transpiler** (not just
  assert injection).
- Test corpus: reuse the ~91 existing files from `tests/to_annotate/` and
  `tests/manually_annotated/`, supplemented with generated edge-case files.
- The annotation language is normalized in `test-suite/annotations.md`.

## Revised Phase 1: Contract-to-Python Transpiler

Build a module (`contract_to_python.py`) that translates each PyCSL
contract construct into an executable Python runtime check.

### Translation rules

| PyCSL construct | Python runtime translation |
|---|---|
| `\result` | Capture return value in `_result_` variable via function wrapper |
| `\old(expr)` | Snapshot `_old_expr_` at function entry, compare at exit |
| `\old(self.field)` | Deep-copy `self.field` at method entry |
| `\forall i; lo <= i and i < hi ==> body` | `all(body_py(i) for i in range(lo, hi))` |
| `\exists i; lo <= i and i < hi and body` | `any(body_py(i) for i in range(lo, hi))` |
| `==>` | `not a or b` |
| `<==>` | `(a) == (b)` |
| `#@ requires expr` | `assert expr_py` at function entry |
| `#@ ensures expr` | `assert expr_py` after return capture |
| `#@ loop invariant expr` | `assert expr_py` before loop, at end of each iteration body, and after loop exit |
| `#@ loop variant expr` | Capture `_prev_variant_`, assert `expr_py < _prev_variant_ and expr_py >= 0` each iteration |
| `#@ assigns \nothing` | Snapshot all mutable params; assert unchanged after call |
| `#@ assigns x` | Snapshot non-`x` params; assert unchanged after call |
| `#@ assigns arr[lo..hi]` | Assert arr elements outside `[lo,hi)` unchanged |
| `#@ class invariant expr` | Assert at method entry and exit |
| `\valid(arr, n)` | `assert len(arr) >= n` |
| `\separated(a, na, b, nb)` | `assert a is not b` (identity check) |
| `\at(expr, L)` | Snapshot at label point, reference in ensures |
| `\length(arr)` | `len(arr)` |
| `arr[i]` | `arr[i]` (direct) |
| `self.field` | `self.field` (direct) |
| `/` in contracts | `//` (Python integer division) |

### Implementation approach

The transpiler **reuses Modules 1-3** from the existing PyCSL pipeline:
1. Module 1 (Ingestor): extracts `#@` comments from source.
2. Module 2 (Parser): parses contract strings into Contract AST nodes.
3. Module 3 (Weaver): attaches contracts to Python AST nodes.

The transpiler then walks the annotated AST and generates an instrumented
Python file by:
- Wrapping functions to capture `\result` and inject pre/postcondition checks.
- Inserting `_old_` variable snapshots at function/method entry.
- Inserting invariant/variant assertions inside loop bodies.
- Translating Contract AST nodes to Python boolean expressions.

This approach reuses the existing parser (avoiding contract language
re-implementation) and ensures the same contract interpretation is used
by both the static and dynamic oracles.

### Limitations to document

Quantifiers over unbounded domains (`\forall i; i >= 0 ==> ...`)
cannot be runtime-tested exhaustively. The transpiler will:
1. Bound the domain to the array length when an array subscript is present.
2. Skip the check and log a warning when no finite bound is derivable.

`\at` requires execution-time snapshots injected at label points,
which means the transpiler must rewrite the function body, not just
wrap it.

## Revised Phase 2: Test Corpus

### Source 1: Existing test files (~91 files)

All `.py` files in `tests/to_annotate/` and `tests/manually_annotated/`
form the base corpus. These already cover:
- Basic functions with pre/postconditions (001-020)
- Classes Levels 2-3 (021-040)
- Array operations (041-055)
- Memory model variants: hoare, typed, store (056-075)
- Label/at expressions (076-080)
- 2D matrices (081-085)
- Quantifiers (086-091)

### Source 2: Generated edge-case files (new)

Generate new test files targeting semantic gaps. **Corrected focus areas:**

1. **Modulo/Division in code body** (not in contracts — `%`/`//` unsupported there):
   - Python code uses `%` with negative operands → verify WhyML `mod` semantics match.
   - Test: function body computes `-5 % 3`, contract asserts `\result == 1` (CPython semantics).

2. **Large integer arithmetic:**
   - Code body uses values > 2^63. Contract asserts exact result.
   - Test: verify WhyML integer theory is unbounded (matching CPython).

3. **Boolean coercion in code body:**
   - `if x:` where `x` is an integer. Verify WhyML translation handles truthiness.

4. **Short-circuit evaluation:**
   - Code body uses `a and f()` or `a or f()`. Verify side-effect semantics.

5. **Negative tests (expected failures):**
   - Correct contracts on buggy code → pycsl should report Invalid, CPython should crash.
   - Wrong contracts on correct code → pycsl should report Invalid, CPython should pass.

6. **Contract edge cases:**
   - Deeply nested quantifiers
   - Multiple `\old` references in one ensures
   - `\at` with multiple labels
   - Class invariant + method contracts combined

## Revised Phase 3: Dual-Execution with Per-Goal Granularity

### Path A (Static Oracle): Run pycsl

```bash
./pycsl <test_file.py> --keep-mlw 2>&1
```

Parse output line by line. Each goal has a result:
- `Valid` — proved
- `Unknown` / `Timeout` — not proved
- `Invalid` — disproved

A function is **Verified** only when ALL its sub-goals are `Valid`.

### Path B (Dynamic Oracle): Run instrumented file

```bash
python3 <test_file_instrumented.py> 2>&1
```

Capture exit code + any `AssertionError` tracebacks.

### Evaluation Matrix (unchanged, but applied per-function)

| Path A (all goals) | Path B (runtime) | Classification |
|---|---|---|
| All Valid | Pass (exit 0) | ✅ SUCCESS |
| Any Invalid/Unknown | AssertionError (exit 1) | ✅ SUCCESS |
| Any Invalid/Unknown | Pass (exit 0) | ⚠️ FALSE POSITIVE |
| All Valid | AssertionError (exit 1) | 🚨 SOUNDNESS BUG |

### Report format

Per-file JSON report:
```json
{
  "file": "086-forall-all-nonneg.py",
  "static_oracle": {
    "exit_code": 0,
    "goals": [
      {"function": "clamp_nonneg", "goal": "precondition", "result": "Valid"},
      {"function": "clamp_nonneg", "goal": "loop_invariant_init", "result": "Valid"},
      {"function": "clamp_nonneg", "goal": "postcondition", "result": "Valid"}
    ]
  },
  "dynamic_oracle": {
    "exit_code": 0,
    "assertion_errors": []
  },
  "classification": "SUCCESS"
}
```
