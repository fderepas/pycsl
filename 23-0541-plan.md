## 2. Track F1 — `sibling_concrete` type-invariant forwarding

**Targets:** GAP 1 (2 sub-goals), GAP 2 (1 sub-goal) — the `_blit_*` uniq / slots_lt32 / inode_bytes_valid maintenance VCs.

**Root cause (from the gap doc):** a `sibling_concrete` helper's single slice write `self.dir[off:off+32] = entry` triggers `uniq`/`slots_lt32`/`inode_bytes_valid` maintenance. The `dir_blit_marker` fold discharges it, but the fold needs the slot INDEX, and the helper only knows the opaque byte offset `off`. The caller (`_write_dir_entry`) knows the slot and cites the marker, but `sibling_concrete` isolates the helper's body VC from the caller's fold.

**Lever:** `getting-better/20260623-1440-slice-write-type-invariant-isolation.md` proposes two options. Both are PyCSL tooling changes (no model change, no axiom). They are mutually exclusive — pick ONE.

### 2.1 Option A — `sibling_concrete` type-invariant forwarding

Let a `sibling_concrete` helper's type-invariant VCs be discharged by the caller's context (which knows the slot and cites the marker). The helper's body VC inherits the caller's marker fold.

- **Semantic justification:** `sibling_concrete` already inlines the helper at the SMT level — the type-invariant VC should be checked at the call site, not in isolation. This is sound because the helper has no independent callers (it is `sibling_concrete`-private to `_write_dir_entry`).
- **Implementation locus:** `src/pycsl/module6_whyml/statements.py` (slice-write handler) + `src/pycsl/module6_whyml/functions.py` (the `sibling_concrete` dispatch).
- **G0 probe:** add a `--type-invariant-at-call-site` CLI flag that, when set, suppresses per-write type-invariant VCs for `sibling_concrete` helpers and emits them at the call site instead. Run on `UnixInodeFileSystem.py` — if the 3 `_blit_*` sub-goals go Valid, the lever works.
- **Gate:** byte-diff DIFFERS=0 on all files NOT using `sibling_concrete`; the 3 `_blit_*` sub-goals Valid; no new `\trusted`.

### 2.2 Option B — `#@ type_invariant_off` directive

A directive that suppresses per-write type-invariant VCs for a helper whose caller maintains the invariant via an explicit marker fold.

- **Implementation locus:** `Module2_Parser.py` (grammar), `Module4_SemanticAnalyzer.py` (validation — reject on a non-`sibling_concrete` function), `Module5_IREmitter.py` (IR field), `module6_whyml/statements.py` (skip the VC).
- **Lighter than Option A** (just an annotation, no emitter branch).
- **Risk:** easier to misuse (a caller could forget the marker fold). Mitigated by Module4 rejecting it unless the function is `sibling_concrete`.

### 2.3 Decision: Option A or B?

See **Decision Point D1** below. The recommendation is **Option A** (no new syntax, semantically tighter — the helper is already declared `sibling_concrete`, so the forwarding is automatic).

### 2.4 Steps

1. **G0 probe** (Option A): add the `--type-invariant-at-call-site` flag, run on `UnixInodeFileSystem.py`, record the 3 sub-goals' verdicts.
2. If the probe passes: make the flag a property of `sibling_concrete` (no CLI flag — automatic), re-run, confirm the 3 sub-goals go Valid.
3. If the probe fails (the marker fold doesn't compose): fall back to **F1-axiom** (see §2.5).
4. Byte-diff gate + proof crosscheck.

### 2.5 F1 fallback — cross-validated `UnixFs.Dir.blit_preserves_uniq` axiom

If the tooling lever fails, write a `UnixFs.Dir.blit_preserves_uniq` lemma (Rocq + Lean, cross-validated), cited via `#@ proof rocq …` / `#@ proof lean …` on `_blit_dir_entry` / `_blit_disk_entry`. This is a **human-gated TCB addition** — the doctrine requires both provers cross-validate and the human approve before merge. The lemma discharges `uniq`/`slots_lt32`/`inode_bytes_valid` maintenance for a 32-byte slice write at a slot-aligned offset.

- **Risk:** the doctrine says "the TCB only ever shrinks" — adding an axiom is a TCB growth. The human must approve.
- **Alternative:** leave these 3 sub-goals as logged GAPs and proceed to F3 (the bigger fish).

## 3. Track F2 — `ord` range ensures on `_build_direntry`

**Target:** GAP 2 `_blit_disk_entry` — 1 sub-goal (the `inode_bytes_valid` byte-range check when `off` falls in [512, 2560)).

**Root cause:** the written bytes (from `_build_direntry`) are `inode_num // 256`, `inode_num % 256`, `ord(name[i])`, `0`. All are provably in [0, 255] for valid inputs, but PyCSL does not constrain `ord`'s range, so the solver cannot derive `0 <= ord(name[i]) <= 255` for the `inode_bytes_valid` byte-range check.

**Lever:** add a `\forall i. 0 <= \result[i] <= 255` ensures to `_build_direntry` so the slice write inherits the byte-range fact. This is a leaf contract — zero-TCB.

### 3.1 Steps

1. **Probe:** add `#@ ensures \forall i: int; (0 <= i and i < \length(\result)) ==> (0 <= \result[i] and \result[i] <= 255)` to `_build_direntry`.
2. Verify the body of `_build_direntry` discharges this (the `inode_num // 256`, `inode_num % 256` branches are [0, 255]; the `ord(name[i])` branch needs an `ord` range fact — see §3.2).
3. Re-run pycsl on `UnixInodeFileSystem.py` — does the `_blit_disk_entry` `inode_bytes_valid` sub-goal go Valid?

### 3.2 The `ord` range sub-problem

If PyCSL has no built-in `0 <= ord(c) <= 255` fact, there are two options:

- **Option (a):** add `0 <= ord(c) <= 255` as a built-in fact in `src/pycsl/module6_whyml/preamble.py` (a `use int.Int` + a constant axiom). This is a tooling change, not a model change.
- **Option (b):** cross-validated `UnixFs.Char.ord_range` axiom (Rocq + Lean), cited via `#@ proof` on `_build_direntry`. This is a TCB addition — human-gated.

See **Decision Point D2**.

## 4. Track F3 — modular verification / separate compilation

**Targets:** GAP 3 `sys_open` (6 sub-goals), GAP 4 `sys_rename` (2 sub-goals). 8 sub-goals — the bulk of the remaining work.

**Root cause (from the gap doc + 09-0702-os-status.md §3):** the full-module E-matching context (40+ cited axioms, the record with 10 class invariants, 50 sibling functions) starves the step budget (OOM) or diverges (Unknown) on the existentially-quantified `dir_lookup` composition + fd-resolution postconditions. **It is proof-cost-bound in aggregate, not foundation-bound** — the mechanism is validated, the context is the blocker.

**Lever (from `09-0702-os-plan.md` §1):** extract the disk-mutating syscalls into a **minimal-context file** so they prove in isolation. PyCSL's import resolver already emits an imported function as a contract-only `val` stub; the syscall module imports the codec + dir helpers' **interface contracts** (cheap), not their bodies. Soundness: the syscall module is itself in the verification suite, so the bodies ARE verified — once, in the cheap context — and the os uses the proven contracts.

### 4.1 File layout

```
src/pycsl_lib/os/
  codec.py              ← already extracted (byte leaves, inode/direntry pack/unpack)
  dir_ops.py             ← NEW: the dir helpers (_dir_lookup, _dir_find_slot, _dir_find_free,
  │                        _write_entry, _zero_entry, _blit_dir_entry, _blit_disk_entry,
  │                        _read_directory, _scan, _build_direntry)
  UnixInodeFileSystem.py ← KEEPS: the record + class invariant + fd table + the syscalls
                           that DON'T need isolation (sys_close, sys_fstat, sys_lseek, …)
  syscalls_disk.py       ← NEW: sys_open, sys_rename, sys_mkdir, sys_unlink, sys_link,
                           sys_symlink, sys_rmdir, sys_truncate, sys_chmod, sys_write, sys_pread
                           (the disk-mutating syscalls that OOM in full-module context)
  __init__.py            ← unchanged (the public os.* wrappers)
```

`dir_ops.py` and `syscalls_disk.py` have **minimal context** (no 131072-byte disk record, no 10 class invariants, no 50 sibling functions) — exactly the context where `_unpack_inode` proved in 12s instead of >300s.

## 6. Decision Points

### D1 — F1: Option A (`sibling_concrete` forwarding) vs Option B (`#@ type_invariant_off` directive)?

**Recommendation: Option A.** It is semantically tighter (the helper is already declared `sibling_concrete`, so the forwarding is automatic — no new annotation to forget), requires no new grammar rule, and is a single emitter change. Option B adds a new directive that must be validated, parsed, and could be misused.

**Open question:** is the `sibling_concrete` dispatch in `module6_whyml/functions.py` the right locus, or does the type-invariant VC emission live in `module6_whyml/statements.py` (the slice-write handler)? The G0 probe will answer this.

**Owner:** the implementer, after the G0 probe.

### D2 — F2: built-in `ord` range fact vs cross-validated `UnixFs.Char.ord_range` axiom?

If `_build_direntry`'s `ord(name[i])` branch can't prove `0 <= ord(c) <= 255` without a fact:

- **Option (a) — built-in fact in preamble.py:** no TCB growth (it's a definitional fact about `ord`), but it's a PyCSL tooling change that affects every module.
- **Option (b) — cross-validated axiom:** TCB growth (human-gated), but no tooling change.

**Recommendation: Option (a).** `0 <= ord(c) <= 255` is a definitional fact (Unicode code points are 0–0x10FFFF, and Python's `ord` on a single char returns a non-negative int; PyCSL models strings as `string` so `ord` is bounded). It belongs in the preamble, not the TCB. But: does PyCSL's string model actually constrain `ord`? If not, Option (b) is the fallback.

**Open question:** does PyCSL's `string` WhyML type have a built-in `ord` range, or is `ord` uninterpreted? Check `src/pycsl/module6_whyml/expressions.py` for the `ord` handler.

**Owner:** the implementer, after checking the `ord` handler.

### D3 — F3: how do the public `os.*` wrappers in `__init__.py` call the extracted syscalls?

When `sys_open` moves to `syscalls_disk.py`, the `open` wrapper in `__init__.py` currently calls `_filesystem.sys_open(filepath, flags)`. After extraction:

- **Option (a):** `UnixInodeFileSystem` imports `sys_open` from `syscalls_disk` and delegates: `sys_open = staticmethod(sys_open_from_syscalls_disk)`. The wrapper calls `_filesystem.sys_open(…)` unchanged.
- **Option (b):** the wrapper calls `sys_open_from_syscalls_disk(filepath, flags, self._filesystem)` directly, bypassing the class. This changes the `__init__.py` wrapper bodies — byte-diff on `__init__.py` will DIFFER.

**Recommendation: Option (a)** — keep the delegation through `UnixInodeFileSystem` so `__init__.py` is unchanged (byte-diff DIFFERS=0 on the public API). The `val` stub interface carries the syscall's contract; `UnixInodeFileSystem` is a thin delegator.

**Open question:** does `sys_open` need access to `self.disk`, `self.fd_open`, etc.? If it's extracted as a free function, it needs them as parameters — which changes the signature and the wrapper. If it stays as a method on a smaller class, the extraction is cleaner. The G0 probe will reveal the minimal signature.

**Owner:** the implementer, after the G0 probe.

### D4 — F3: is the `sys_rename` lemma worth writing now, or defer?

If the F3 G0 probe shows `sys_rename` proves in minimal context → no lemma needed. If not → `UnixFs.Dir.rename_presence_absence` is a human-gated TCB addition.

**Recommendation: defer.** Run the F3 extraction first; only write the lemma if `sys_rename` still fails in minimal context. The doctrine says "the TCB only ever shrinks" — adding an axiom is a last resort, and `sys_rename` has been a logged GAP for months without blocking the rest of the os.

**Open question:** does the mission require `sys_rename` to be closed, or is a logged GAP acceptable? The `test-supervise-sl.md` doctrine says "an unprovable target is an honest GAP, never a trusted 'done'" — so a logged GAP is acceptable. The human decides whether to prioritize the lemma.

**Owner:** the human.
