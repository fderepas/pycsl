# 07-2333-req — PyCSL: Richer Type Support in Formal Tests

**Date:** 2026-06-07  
**Context:** After the P2–P5 seq-promotion merge (`db88d3e`), formal test drivers
can already prove properties involving strings, list element access, and `len()`.
However, several patterns that *should* be expressible within the WhyML type system
fail due to code-generation or type-inference gaps in the PyCSL transpiler.  This
requirement captures the six broken patterns, their root causes, and the expected
behaviour once fixed.

---

## Gap 1 — String local variable binding

### Symptom

```
This expression has type string, but is expected to have type int
```

### Reproducer

```python
from pure_lib.htm import escape

def test() -> str:
    r: str = escape("hello")   # ← fails
    return r
```

### Root cause

Local variables are unconditionally lowered to WhyML `int` refs regardless of the
annotated Python type.  When the RHS is a call to a function that returns `string`,
the assignment attempts `int := string`.

### Expected fix

Module6 should propagate the type annotation (or infer from the RHS stub signature)
and emit `let r = ref (result : string) in` for `str`-annotated locals.

## Gap 2 — String concatenation

### Symptom

```
This expression has type string, but is expected to have type int
```

### Reproducer

```python
def test() -> str:
    a: str = "he"
    b: str = "llo"
    return a + b     # ← lowered as int + int
```

### Root cause

The `+` operator is unconditionally emitted as integer addition.  No dispatch exists
for the case where both operands are `string`-typed; WhyML's `String.concat` (or
`(^)`) should be emitted instead.

### Expected fix

When both operands of `BinOp(Add)` are known to be `str`-typed (via annotation or
inference), emit `String.concat a b` or the infix `(^)` operator in WhyML.

## Gap 3 — List growth via `+=` (seq/int type mismatch)

### Symptom

```
This expression has type seq.Seq.seq int, but is expected to have type int
```

### Reproducer

```python
def test(n: int) -> int:
    items: list = [0]
    items += [1]     # ← seq-promoted, but loop context still expects int
    return len(items)
```

### Root cause

P3 correctly seq-promotes `items` (marks it as `ref (seq int)`), but the subsequent
`len(items)` or usage in postconditions attempts to unify `seq int` with the `int`
type expected by the surrounding context.  The boundary between seq-promoted locals
and the rest of the WhyML emission is incomplete.

### Expected fix

After seq-promotion, all uses of the variable (len, indexing, return, assignment to
other locals) must respect the `seq int` type.  `len()` on a seq-promoted variable
should emit `Seq.length !items`.

## Gap 4 — Passing lists cross-module (array vs int parameter type)

### Symptom

```
This expression has type array.Array.array int @rho,
but is expected to have type int
```

### Reproducer

```python
from pure_lib.json import dumps

def test() -> str:
    return dumps([1, 2, 3])   # ← caller creates array, stub param typed int
```

### Root cause

Imported stub signatures are generated with `int` parameter types regardless of the
actual Python type annotation.  After P4/P5, list literals at the call site are now
correctly typed as `array int`, creating a mismatch with the callee's `int` parameter.

### Expected fix

When a pure_lib stub parameter has a `list` annotation (or accepts `Any`/untyped and
the call site passes a list literal), the imported stub signature should declare
`array int` (or `seq int`) for that parameter.

## Gap 5 — Quantifiers referencing local variables in postconditions

### Symptom

```
unbound function or predicate symbol 'items'
```

### Reproducer

```python
#@ ensures \forall i; (0 <= i and i < 3) ==> items[i] >= 0
def test() -> int:
    items: list = [10, 20, 30]
    return items[0]
```

### Root cause

Postcondition expressions are emitted in the function's contract scope, which does
not have visibility into local variables.  WhyML only allows `\result` and formal
parameters in postconditions.

### Expected fix

This is a fundamental WhyML/ACSL limitation — local variables cannot appear in
postconditions.  Two workarounds:

1. **Use loop invariants** instead (already works):
   `#@ loop invariant \forall i; (0 <= i and i < len) ==> items[i] >= 0`
2. **Expose via return** — return the list and use `\result[i]` in the postcondition
   (requires Gap 4 to be fixed first for cross-module cases).

Mark this as *won't fix in postconditions*; document the loop-invariant pattern.

## Gap 6 — Class invariants / fields with str type

### Symptom

```
This term has type int, but is expected to have type string
```

### Reproducer

```python
""" # pycsl"""
class Greeter:
    #@ class invariant self._name == "world"
    def __init__(self) -> None:
        self._name: str = "world"
        #@ assigns self._name

    #@ ensures \result == "world"
    #@ assigns \nothing
    def greet(self) -> str:
        return self._name
```

### Root cause

Class record fields are unconditionally generated as `int` in WhyML regardless of
the Python type annotation.  When a class invariant or method postcondition references
a field with a string literal (`self._name == "world"`), the emitted WhyML compares
`int` to `string`.

### Expected fix

Extend class record generation (Module6) to infer or propagate field types from
annotations.  A `str`-annotated field should emit `_name: string` in the WhyML record
type.  This is the class-level counterpart of Gap 1 (str locals).

## Gap 7 — Class field tracking through chained method calls

### Symptom

```
Prover result is: Unknown (sat)
```

### Reproducer

```python
""" # pycsl"""
class Counter:
    #@ class invariant self._count >= 0
    def __init__(self, start: int) -> None:
        self._count: int = start
        #@ requires start >= 0
        #@ assigns self._count
        #@ ensures self._count == start

    #@ assigns self._count
    #@ ensures self._count == \old(self._count) + 1
    def inc(self) -> None:
        self._count = self._count + 1

    #@ ensures \result == self._count
    #@ assigns \nothing
    def get(self) -> int:
        return self._count

#@ ensures \result == 5
def test() -> int:
    c = Counter(3)
    c.inc()
    c.inc()
    return c.get()   # ← prover cannot chain 3 + 1 + 1 = 5
```

### Root cause

After each method call, the prover's knowledge of class fields is limited to the
callee's postcondition.  The Hoare record model does not automatically maintain
equality chains across sequential calls.  `Counter(3)` guarantees `_count == 3`,
`inc()` guarantees `_count == old + 1`, but after two `inc()` calls the second
`\old(self._count)` refers to the post-state of the first call which the prover
cannot name.

### Expected fix

Two approaches:
1. **Ghost variable / assertion** — allow `#@ assert c._count == 4` between calls to
   give the prover stepping stones.
2. **Frame condition strengthening** — emit `ensures self._count == \old(self._count) + 1`
   as a *functional* update (record-with syntax) so the prover accumulates knowledge.

Priority: medium.  The parametric loop version (with loop invariant) already works for
the same class, so this is an ergonomics issue rather than a soundness gap.

## Gap 8 — Exception declarations in imported stubs

### Symptom

```
this expression raises unlisted exception Exception
```

### Reproducer

```python
from pure_lib.warn import warn

def test() -> int:
    warn("something", 0, 1)   # ← stub body raises Exception
    return 0
```

The `pure_lib/warn/__init__.py` stub contains:
```python
def warn(message, category, stacklevel):
    ...
    raise Exception(message)
```

### Root cause

When a pure_lib stub body uses `raise Exception(...)`, the generated WhyML function
does not declare `raises { Exception }` in its signature.  The caller then fails at
type-checking because the callee raises an exception not listed in its contract.

### Expected fix

Two options:
1. **Auto-detect `raise`** — during stub import, if the function body contains a
   `raise` statement, emit `raises { Exception }` in the WhyML function signature.
2. **Contract annotation** — allow `#@ raises Exception` in the stub's contract so
   the user explicitly declares which exceptions a function may raise.

The caller must then either handle the exception or also declare it.

## Gap 9 — World model symbols not visible cross-module

### Symptom

```
unbound function or predicate symbol 'fd_io'
```

### Reproducer

```python
from pure_lib.world import World
from pure_lib.os.UnixInodeFileSystem import UnixInodeFileSystem
from pure_lib.iomod import FileIO, set_world, open_file

w = World()
fd_io = w.fs.sys_creat("test.txt", 0o644)   # fd_io used later
fio = FileIO(fd_io, w.fs)
n = fio.write(b"abc")
```

### Root cause

When a module-level variable (`fd_io`) is assigned the result of a method call on an
imported class (`w.fs.sys_creat(...)`), the WhyML emitter fails to track it as a
named local in the enclosing scope.  Later references to `fd_io` generate an unbound
symbol error because the variable was never introduced in the WhyML `let` chain.

This primarily affects "test script" patterns where multiple cross-module operations
are sequenced at module top-level (outside a function body).

### Expected fix

Ensure that module-level assignments of method-call results generate proper `let`
bindings in the WhyML output.  The variable's type should be inferred from the
method's return annotation (here `sys_creat` returns `int` — a file descriptor).
