## R1 — `assigns \nothing` → `writes { }` on `val` stubs

**Why the current code misses it.** `_emit_frame_condition` short-circuits to `[]` when
`self._value_semantic` (the Hoare model the `os` module uses), on the premise that
value-semantic arrays can't alias. That premise holds for functions **with bodies** (Why3
infers their effects), but a body-less `val` has *no inferable effect set* — Why3's default
is "may write anything in scope," including the mutable global `_filesystem`. So every call
to an `assigns \nothing` helper stub clobbers the prover's knowledge of `_filesystem`'s
fields. An empty `writes { }` is the sound encoding of "modifies nothing."

**Fix.** In the `emit_as_val` branch of `_emit_one_function` (functions.py:~331), when the
contract's `assigns` is a `Nothing` node, emit `writes { }` **regardless of memory model**.
Concretely: thread an `is_val` flag into the contract/frame emission, and in
`_emit_frame_condition` add, *before* the `if self._value_semantic: return []` guard:

```python
nothings = [a for a in assigns_list if a.get("type") == "Nothing"]
if is_val and nothings:
    return ["    writes   { }"]          # body-less stub modifies nothing — sound
```

- Place the `writes { }` line in the contract order shown in `1009.md` (after `requires`,
  before `ensures`).
- **Edge to decide (note in driver docstring):** a `val` stub with a *non-empty* `assigns`
  (specific regions) in the value-semantic model currently also emits no `writes`. R1 scopes
  only to `\nothing`; flag the broader body-less-`val` effect-set question as follow-up, do
  not silently widen.

**Driver(s).**
- `1010` (positive): a module global with a field array; a free helper `#@ assigns \nothing`
  returning an `int` derived from an `array int` param; a driver that (a) reads a global
  field, (b) calls the helper, (c) proves the field fact still holds afterward. RED on
  baseline (fact lost), GREEN after R1.
- Confirm the emitted stub shows `writes { }` (byte-grep the `--keep-mlw` output).

## R2 — length postcondition on `encode`/`ljust`/`rjust`/`zfill` stubs

**Refinement of the requirement.** The blocking precondition is
`_pack_direntry`'s `\valid(name_bytes, 30)` (`Array.length >= 30`). In the source that 30 is
*established* by `name.encode('utf-8')[:30].ljust(30, b'\x00')` — i.e. **`ljust(30)` pads to
exactly 30**, not `encode`. So the precise, faithful fix is on the *padding* family, with a
conservative floor on `encode`:

- **`encode(...)`** → `ensures { Array.length result >= 0 }` (always sound; Option A). A
  non-emptiness claim (`> 0`) is **not** sound for `"".encode()`, so do not emit it
  unconditionally.
- **`ljust(N, …)` / `rjust(N, …)` / `zfill(N)`** with a **literal** width `N` →
  `ensures { Array.length result = N }` (exact — these pad/extend to N). This is the
  postcondition that actually discharges `\valid(name_bytes, 30)`. Derive `N` from the
  literal first argument at the call site (already visible in the IR).
- If the width is non-literal, fall back to no length claim (and `log` the limitation).

**Fix location.** The bytes-producing-method stub emission reached from `expressions.py:673`
/ `_handle_dotted_call`. When emitting the abstract `val <name>_<method>_<n> (…) : array int`,
attach the `ensures` above based on `method_tail_name` and the literal-width argument.

**Driver(s).**
- `1011` (positive): `s.encode('utf-8').ljust(30, b'\x00')` flowing into a function requiring
  `\valid(x, 30)`; prove the precondition discharges. RED on baseline.
- `1012` (negative, `# pycsl-expected: FAIL`): claim `Array.length >= 31` after `ljust(30)` →
  unprovable (confirms the length is exact/precise, not over-claimed).

## R4 — `assigns \nothing` propagation through inlining

**Mostly a consequence of R1.** The inliner splices a method *body*; a helper call inside it
remains a call to the **single shared** `val` stub declaration. So once R1 puts `writes { }`
on that declaration, every inlined call site inherits it — there is no per-call-site stub to
strip. The risk to rule out: the inliner emitting a *separate*, contract-less stub for the
inlined occurrence, or dropping the callee's `assigns` metadata.

**Plan.**
1. After R1, driver `1014`: a method that calls an `assigns \nothing` helper, inlined into a
   driver on a module global; assert (a) the emitted helper `val` carries `writes { }`, and
   (b) a global-field fact established before the inlined helper call survives after it.
2. Inspect `ir_inline.py` (`_expand`) to confirm it neither rewrites nor re-emits the callee
   contract — it should leave the helper as an ordinary call. If it does interfere, fix there.

## OUTCOMES (execution log — supersedes the speculative impact estimates above)

Implemented in order; each finding is evidence-backed.

### R3 — ✅ DONE (driver 0587), no code change
`\result[N]` on a tuple result already lowers to a per-component `let (_r0_, _) = result in …`
destructure — and it fires for `val` stubs too (arity inferred from the body return), with the
constraint flowing through a tuple-unpack consumer (`a, b = f()`). Verified for both a body
function and a trusted `val`. The only residual is body-side `p[0]` indexing on a tuple local
(emits `subscript_get`), which the `os` module does not use. Driver `0587` locks it in.

### R1 — ❌ PREMISE FALSE (reverted), with proof
A Why3 `val` with no `writes` clause is **already effect-free** — val effects are explicit, so
"no writes" = writes nothing. Decisive test: a writes-less `val gadget(a: array int)` does NOT
let the prover lose `arr`'s contents in the caller (the equality `arr[0] == \old(arr[0])`
across the call proves); same for a scalar global field. So `assigns \nothing → writes { }` is
a **sound no-op**, not the cause of the 148 failing VCs. Per the gating discipline (no change
without a RED→GREEN driver) it was reverted. The implementation was correct and harmless; it
simply fixes nothing.

### R4 — ❌ MOOT
Depends on R1. Since writes-less vals are already effect-free, there is no `writes { }` to
propagate through inlining.

### R2 — ✅ DONE (drivers 0588 / 0589)
Two sound, gateable changes:
1. `s.ljust(w)/rjust(w)/zfill(w)` stubs now emit `ensures { Array.length result >= x0 }` (the
   width `w` is the first arg; Python pads to at least `w`). `encode` is left unconstrained
   (its length is genuinely unknown; `>= 0` would be vacuous).
2. A local bound to a bytes-producing method result is now tracked as array-typed (was `ref 0`
   → hard type error). `bin/.../ir_scanner.py::find_array_and_dict_vars`.
Together they discharge a downstream `\valid(x, 30)`. RED→GREEN on `0588`; `0589` (negative)
confirms the bound is exactly the width, not an over-claim.
**Caveat:** the actual `8d9f749` `os` code pads via `(name_bytes + b'\x00'*30)[:30]`
(slice+concat), NOT `ljust/zfill`, so R2 may not directly move the `os` VC count — it fixes the
construct R2 *describes*. A separate fill-char-arg typing bug (`ljust(w, b'\x00')` types the
fill as `int`) is noted but out of scope.

### Real blocker discovered (NOT in 1009.md)
Reading a module-global record's **array field** by subscript (`d.disk[3]`) emits the abstract
`subscript_get (x:int)` against an `array int` → hard type error. This is the same class as the
`arity2.md` 2b fix but for **record fields**, and is a plausible source of report.md's 45
"Index in array bounds" failures. Recommend this as the real R-prime to pursue for the `os`
module, in place of R1/R4.

### Net
R3 + R2 land (3 drivers: 0587/0588/0589). R1/R4 do not (no-ops). The 148-VC estimate attributed
to R1 is unfounded; the real lever is the record-array-field read gap above.
