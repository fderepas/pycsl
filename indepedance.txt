Independence Strategy — PyCSL Project
======================================

PyCSL is designed to be independent of any specific LLM provider and any
specific agent harness.  This document explains the architectural decisions
that make this possible.


1. HARNESS INDEPENDENCE
-----------------------

1.1  No reserved dotfile directories

    Many agent runtimes auto-discover skills, personas, and tools from a
    hidden directory at the project root (e.g. `.cursor/`, `.copilot/`).
    PyCSL avoids this entirely: all configuration lives under `config/`,
    a plain, visible directory that any runtime can be pointed at.
    Migrating to a different harness means telling the new runtime where
    `config/` is — not renaming directories.

1.2  The SKILL.md cross-vendor contract

    Every skill is a folder containing a `SKILL.md` file with YAML
    frontmatter (`name` and `description` at minimum), plus optional
    `scripts/`, `references/`, and `assets/` subfolders.  This is the
    only structural convention the project enforces, and it is the one
    convention that is emerging as a de-facto standard across multiple
    agent runtimes.  A skill written for PyCSL can be loaded, unchanged,
    by any harness that understands the SKILL.md format.

1.3  Declarative agent personas

    Agent identities (system prompts, allowed tools, model preferences)
    are stored as plain markdown files in `config/agents/`, one file per
    persona (e.g. `agent-annotate.md`, `agent-reconcile.md`).  They are
    not embedded in Python code, not encoded in a vendor SDK's object
    model, and not tied to any specific orchestrator.  Any runtime that
    can read markdown can load them.

1.4  Configuration is data, not code

    `config/agents-config.json` holds model names, skill paths, prover
    settings, and RAG parameters as plain JSON.  Swapping a model, a
    prover, or a memory model is a one-line config change — no code
    modification required.


2. LLM INDEPENDENCE
-------------------

2.1  Abstraction layer: llm_client.py

    All agent scripts call a single shared module (`llm_client.py`) to
    interact with an LLM.  The module currently supports Ollama's local
    API and GitHub Copilot, but its interface — "send a system prompt
    and a user prompt, receive a string or parsed JSON" — is deliberately
    minimal and provider-agnostic.  Switching to a different provider
    (OpenAI, Anthropic, a corporate gateway) requires changing only
    this one file.

2.2  Model name is configuration

    The model tag (e.g. `gemma4:31b`, `claude-sonnet-4.6`) is read from
    the `MODEL_NAME` environment variable or from `agents-config.json`.
    No agent script hard-codes a model name.

2.3  Skills encode knowledge, not API calls

    Skills are written in plain English and mathematical notation.  They
    describe *what* the LLM should do ("write a postcondition that
    captures the function's purpose"), not *how* a particular API should
    be called.  This means the same skill text works whether the backend
    is a 7B local model or a frontier cloud model — the quality of the
    output changes, but the instructions remain valid.

2.4  RAG is model-decoupled

    Skills under `config/skills/` are source content.  Their RAG-derived
    form (chunks + embeddings + vector index) lives separately under
    `data/embeddings/` and is rebuilt on demand by `bin/update-rag.sh`.
    The embedding model is recorded in a manifest alongside the index.
    Switching embedding models means re-running the build script — the
    skills themselves do not change, and no embedding artifacts are ever
    bundled inside a skill folder.


3. THE CORE PIPELINE IS LLM-FREE
---------------------------------

The heart of PyCSL — Modules 1 through 6 — is a deterministic compiler
pipeline that transforms annotated Python into WhyML:

    Module1 (Ingestor) → Module2 (Parser) → Module3 (Weaver)
    → Module4 (Semantic Analyzer) → Module5 (IR Emitter)
    → Module6 (WhyML Transpiler) → Why3 / Alt-Ergo / Z3

This pipeline contains zero LLM calls.  It is pure Python code that
parses an EBNF grammar, builds an AST, emits an IR, and generates
WhyML.  The SMT solvers (Alt-Ergo, Z3) are also deterministic tools.

The LLM is used only by the *agent layer* that sits above the pipeline:
agents generate the `#@` annotations (contracts, invariants) that the
pipeline then compiles and proves.  If a team wanted to write contracts
by hand, they could bypass the agents entirely and use the pipeline
directly — `pycsl myfile.py` works with or without any LLM.


4. PORTABILITY CONSEQUENCES
----------------------------

These design choices have concrete practical consequences:

  - A developer can run the full proof pipeline on a laptop with no
    internet connection and no LLM, provided the annotations are
    already written.

  - A team can switch from Ollama + gemma4 to Claude via API by
    editing one config key and one Python file, without touching any
    skill, any agent persona, or any pipeline module.

  - Skills written for PyCSL can be shared with other projects that
    follow the SKILL.md convention, even if those projects use a
    completely different orchestrator.

  - The RAG index can be rebuilt from scratch at any time, with any
    embedding model, without modifying any source file.  Staleness is
    detectable via the manifest.

  - New agent harnesses can be adopted by pointing them at `config/`
    (or symlinking from the harness-expected location).  The project's
    source of truth stays in one place.
